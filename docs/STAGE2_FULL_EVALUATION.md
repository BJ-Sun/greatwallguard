# 阶段二：类型化效果授权与双基准全量评估

> 本文记录截至当前最好的非生成式结果。优化只使用部署级工具契约、效果类型和运行时事实，不读取攻击标签，也不针对任务 ID 或已知 case 添加规则。

## 1. 这次完成了什么

阶段二不是一个攻击分类器，而是一个运行在工具调用前后的**授权证明器**。它接收阶段一生成的授权 DAG，并持续读取实际工具调用、参数、工具返回和状态版本，尝试证明当前行为仍属于用户授权。

```text
用户授权 DAG
      │
      ├── 允许的终端效果、固定参数、动态参数槽和约束
      │
实际调用 ── 工具 + 参数
      │
实际返回 ── 字段值 + 来源调用 + 字段路径 + 状态版本
      ▼
运行时证明器
      ├── ALLOW：授权关系已被程序证据证明
      ├── REVIEW：没有发现冲突，但证据不足
      └── ALERT：效果、参数、范围、预算或版本明确冲突
```

当前实现已固定以下通用能力：

- 字段级来源：记录某个值来自哪次调用、哪个工具和返回中的哪个字段；
- 有限关系算子：投影、筛选、连接、聚合、规范化、计算和模板变换；
- 范围传播：目录到子路径、限定 URL 范围和对象范围，禁止向兄弟路径或其他域扩张；
- 中间能力：允许从已授权终端效果派生必要的临时操作，但必须保留对象或参数关联；
- 类型化效果：未经授权的终端效果直接告警；只有部署契约声明为某个授权目标之前置能力的工具，才可能作为中间操作进入证明或复核；
- 动态预算：可按对象绑定计数，允许多个不同对象各执行一次，同时阻止同一对象重复执行；
- 版本证据：记录状态写入与回读的版本；未授权版本不能作为后续敏感参数的证明；
- 在线状态：支持成功提交、失败回滚、撤销和快照恢复。

整个阶段二不调用 LLM，也不读取模型隐藏推理。

## 2. 实验回答什么问题

实验检验两个问题：

1. 标准正常轨迹中的真实调用，有多少能被程序证据自动证明，而不需要人工或 LLM？
2. 官方攻击目标调用出现时，有多少会被直接放行、进入复核或被高置信阻断？

本次使用 AgentDojo 全部 97 个正常任务和 629 个任务—攻击组合，以及 AgentDyn 三个 suite 的 60 个正常任务和 560 个任务—攻击组合。授权 DAG 只根据可信用户请求和工具 schema 生成，攻击文本与攻击轨迹不参与授权生成。

评估采用**标准轨迹条件回放**：正常侧执行基准的标准工具序列并收集真实返回；攻击侧在相同授权和运行时证据下检查官方攻击目标调用。因此，结果衡量的是防御器对候选调用的判定能力，不等同于重新运行受害模型后的端到端 ASR 或任务成功率。

## 3. 关键规则：终端效果不能伪装成动态步骤

早期实现把所有已知 effect tool 都视为“可能是正常动态步骤”。因此，一个未出现在授权 DAG 中的发送、转账或删除操作不会被直接放行，却通常只进入 `REVIEW`。这避免了正常误阻断，也把大量明确新增的攻击效果降成了低置信结果。

最新规则不根据工具名临时列黑名单，而使用部署方提供的能力关系：

```text
调用已被授权 DAG 覆盖
        └── 按参数、来源、范围、预算和版本继续证明

调用未被授权 DAG 覆盖
        ├── 是已声明的中间能力
        │      ├── 与授权终端效果的参数关系成立 → ALLOW
        │      └── 关系尚未证明 → REVIEW
        └── 是新增终端效果 → ALERT
```

例如，`cart_add_product` 可以是 `checkout_selected_cart` 的前置能力，`git_clone / move_node` 可以是一次已授权仓库发布的工作区准备步骤；但一个没有终端授权支持的 `send_money` 不能仅因为它是系统已知工具而降级为复核。能力边来自工具或应用契约，不从测试 case 反推。

## 4. 全量结果

### AgentDojo

| 数据 | ALLOW | REVIEW | ALERT |
|---|---:|---:|---:|
| 正常任务（97） | 60（61.9%） | 37（38.1%） | 0 |
| 全部攻击组合（629） | 20（3.2%） | 179（28.5%） | 430（68.4%） |
| 有实际目标动作的攻击（609） | 0 | 179（29.4%） | 430（70.6%） |

20 个 `ALLOW` 均是基准中攻击目标序列为空的组合。对 609 个存在实际目标动作的组合，阶段二没有直接放行，其中 430 个已经能够高置信阻断。

### AgentDyn

| 数据 | ALLOW | REVIEW | ALERT |
|---|---:|---:|---:|
| 正常任务（60） | 6（10.0%） | 54（90.0%） | 0 |
| 攻击组合（560） | 0 | 337（60.2%） | 223（39.8%） |

60 个任务均成功生成合法授权 DAG，60 条正常标准轨迹均完成执行。AgentDyn v1.2.2 的一个标准轨迹仍使用旧参数名 `discount`，而工具接口已改为 `discount_code`；评估适配器只在执行边界转换该别名，防御器仍审计原始标准参数。AgentDyn 的正常自动放行率显著低于 AgentDojo，说明开放动态任务中的参数委托、中间网页操作和外部结果驱动关系，尚难由当前有限证明自动闭合。

### 与保守策略的受控对比

| Benchmark | 正常 ALERT | 有效攻击直接 ALLOW | 攻击 ALERT：调整前 | 攻击 ALERT：调整后 |
|---|---:|---:|---:|---:|
| AgentDojo | 0/97 | 0/609 | 45/609（7.4%） | **430/609（70.6%）** |
| AgentDyn | 0/60 | 0/560 | 12/560（2.1%） | **223/560（39.8%）** |

AgentDyn 第一轮严格化曾把两个正常仓库任务判为 `ALERT`。它们都需要在已授权仓库效果之前执行 `git_clone / move_node / git_push`。我们没有按任务加入例外，而是补齐部署级仓库能力关系；这些操作只有在图中存在相应终端授权时才可降为 `REVIEW`，独立出现仍然告警。最终两个 benchmark 的正常硬误报均为 0。

## 5. 结果说明了什么

第一，阶段二已经形成可复用的安全内核，而不是针对单个任务添加规则。相同的授权 DAG、字段来源、范围传播、预算、版本和类型化效果机制可直接运行在两个结构不同的 benchmark 上；当前 366 项测试全部通过，两个基准的正常任务均没有被判为明确冲突。

第二，`REVIEW` 不能被当作攻击检出。类型化效果把高置信阻断率提高到 AgentDojo 70.6%、AgentDyn 39.8%，且没有增加正常硬误报；但若把剩余 `REVIEW` 全部阻断，正常任务自动通过率仍只有 AgentDojo 61.9%、AgentDyn 10.0%，不可作为最终部署策略。

第三，剩余问题集中在**正向授权证明**，而不是继续增加危险行为黑名单。AgentDyn 正常复核的主要原因是：动态参数虽然来自外部结果，但授权图没有精确表达外部内容可以决定哪个字段；中间操作与终端效果之间缺少可验证的参数连接；开放文本和生成内容需要理解任务语义；部分读取或出站观察缺少明确部署契约。

按调用级原因归类后，AgentDyn 正常轨迹共产生 154 个复核原因：36 个仍属于程序或部署证据不足，例如观察工具缺少契约、中间能力缺少参数连接；118 个涉及动态字段委托、开放文本、条件含义或对象身份，不能仅靠已有事实证明。AgentDojo 共产生 64 个正常复核原因，其中 12 个是出站观察或动态预算等程序关系，52 个涉及字段绑定或外部内容委托。一个任务可能包含多个原因，因此这些数字不能直接换算成任务准确率，但它们说明继续完善少量通用契约只能解决一部分复核，剩余主体确实需要受限语义判断。

因此阶段二的完成边界是：程序可观察的效果类型、来源、范围、有限变换、预算和版本关系已经被组织为固定算法；无法由这些关系证明的语义委托必须显式输出 `REVIEW`，不能靠放宽白名单伪装成已解决。

## 6. 哪些还能继续程序化解决

剩余复核不能按“某个 benchmark 中从未出现在正常样本里的工具或原因”直接升级为攻击。这样的规则利用了测试分布，不具备现实泛化能力。后续程序化改进只接受以下四类输入：

1. **工具契约。** 工具开发者声明观察工具是否被动、是否可能出站，以及某项能力能否作为另一终端效果的前置步骤。
2. **字段类型与所有权。** schema 声明字段是用户固定、运行时生成、允许由外部数据填写，还是必须保持为空；外部内容不能自行改变字段所有权。
3. **可重放关系。** 通过字段级来源和有限算子证明投影、筛选、连接、计算、路径包含和版本传播，不根据自然语言猜测。
4. **资源不变量。** 次数预算、对象范围、路径／域范围、状态版本和撤销均由宿主程序维护。

据此，仍有一部分 `REVIEW` 可以继续程序化收敛，例如：为工具 schema 补充标准化 observation contract；为通用工作流声明带参数连接的能力边；把“精确字面量”和“模型生成展示文本”区分为不同字段类型；在真实执行中补齐状态对象和版本标识。

以下关系不应继续伪装成程序规则：外部资料中的哪个对象符合用户描述；同一来源中的值是否具有当前任务所需的业务权威；生成正文是否忠实于用户目的；两个语义相近但字面不同的条件是否等价。这些属于阶段三的最小局部语义审计。

## 7. 与相关工作的关系

这次改进与现有工作形成了清晰对应，但判定载体不同。

- **CaMeL**依靠 capability、dependency 和人工 policy，默认不可信数据不能改变特权控制流。我们的能力边同样必须来自部署契约，但只约束效果授权，不要求提前固定完整控制流；没有参数连接的中间能力只能进入复核。
- **AUTHGRAPH**通过 Hard Block 和 Tool Name Check 拦截计划外调用，再以参数来源图处理 wrong-source attack。我们的实验也证明工具／效果级偏差提供强信号，但我们匹配的是终端效果与可派生能力，不把 Planner 给出的一条工具序列当作唯一正常计划。
- **PAuth**把任务编译为受限程序，并通过权威服务提供的来源 envelope 证明参数计算。我们的有限关系算子采用相近的“可验证计算”原则，但还必须处理本地文件、记忆和工作区版本缺少权威服务器背书的情况。
- **AttriGuard**用弱化 observation 后的 shadow replay 判断动作是否由外部内容驱动，并依赖辅助 LLM 做改写和语义匹配。它适合处理程序来源不足的因果信号；我们的阶段二则先穷尽无需 LLM 的授权证明，把真正的语义未决关系留到阶段三。

这些工作共同说明，高攻击阻断率可以来自严格控制流、计划外调用阻断或 LLM 反事实判断。我们的目标不是用更多 case 规则追平数字，而是在容忍动态执行的前提下，明确每一次自动放行或阻断所依赖的可迁移证据。

## 8. 下一步

下一步进入阶段三，但不是把整条轨迹交给 LLM 重判。系统只从 `REVIEW` 中提取一个最小未决关系，例如：

```text
用户是否授权“搜索结果中的最高评分酒店”填入 booking.hotel_id？
当前值 H17 来自 search_hotels.items[2].id；
items[2].rating = 4.8，是否满足授权条件？
```

局部审计器只输出 `SUPPORTED / CONTRADICTED / INSUFFICIENT`，不能新增终端效果或扩大范围。正式实验应比较：加入局部审计后，AgentDojo 的 37 个正常复核和 AgentDyn 的 54 个正常复核能减少多少，同时 609 与 560 个攻击调用中有多少仍不会被错误提升为 `ALLOW`。

## 9. 防止补丁式优化的实验纪律

后续每个程序化算子必须同时满足：

- 定义时不读取攻击标签、任务 ID 或测试结果；
- 能从工具 schema、部署契约或有限关系代数中独立推出；
- 在至少两个不同任务或两个 benchmark 上具有相同语义；
- 同时报告正常 `ALLOW/REVIEW/ALERT` 和攻击 `ALLOW/REVIEW/ALERT`；
- 新规则先冻结，再在未参与设计的任务上测试；
- 不能证明的关系保留 `REVIEW`，不通过阈值包装成高置信结论。
