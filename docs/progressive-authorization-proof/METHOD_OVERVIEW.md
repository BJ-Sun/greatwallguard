# GreatWallGuard 方法概览：Progressive Authorization Proof

正常 Agent 的工具路径和参数具有动态性，无法在执行前穷举；但如果把动态规划完全交给 Agent，攻击者又可以借外部网页、邮件、文件或记忆影响规划，新增工具、替换参数并扩大最终效果。例如，用户只要求购买一台相机，正常 Agent 可能动态搜索商品、查看详情、加入购物车并结算；恶意网页也可能诱导它额外发送用户信息。固定工具序列会误拦前者，完全开放工具选择则会放过后者。由此，我们关注在执行路径和具体参数尚未确定的条件下，动态产生的行为能否持续由用户授权解释。

长程攻击可以把目标拆成多个局部合理的步骤，但要跨步累积并最终造成可观察危害，至少一个步骤必须留下可被后续利用的状态，或直接改变外部环境。我们将这类安全相关的真实后果统一定义为 **Effect**，包括发送消息、转账或购买、删除或发布资源、修改文件与配置、写入记忆、改变权限和凭据，以及创建可在后续触发的任务；其中，最终实现用户目标或攻击目标的后果称为终端 Effect。Effect 的授权由工具语义与关键参数的形成过程共同决定。我们将关键参数从用户字面值或运行时数据出发、经过筛选和计算后流入 Effect 的关系定义为 **Binding**。由此，防御问题可以转化为：在 Effect 即将发生或持久状态即将被后续使用时，识别用户授权行为与被误导 Agent 行为之间的差异。该差异由简到难依次表现为：新增终端 Effect；工具路径不同但可能是正常动态执行；同一工具下固定参数错误；动态 Binding 的来源或计算过程错误；以及工具、来源和数据流均相似、只有任务语义不同。仍以购物任务为例，额外发送邮件属于新增 Effect，`add_to_cart` 可能只是正常中间工具，购买数量错误属于固定参数冲突，购买的商品不是搜索结果中评分最高者属于动态 Binding 冲突，而“最适合出差的相机”是否对应某个候选商品则属于语义未决关系。

我们的目标是在不固定唯一执行路径的情况下，为每个真实 Effect 建立一条从可信用户请求到实际工具调用的授权证明。关键观察是：无论执行过程如何动态变化，外部内容都不能自行新增终端 Effect、扩大被操作的对象和数据范围，或绕过用户规定的条件与预算。基于这一边界，我们提出 **Progressive Authorization Proof**：差异越明显，越优先使用便宜、确定且可复核的程序证明；只有当 Effect、工具能力、参数来源和计算过程均无法形成明确结论时，才将剩余的一条局部语义关系交给受约束的语义审计模块。审计模型仅接收程序确定的原子问题及其最小证据，并在既有 Effect、字段和候选值范围内给出结论。整个验证过程按照授权关系的可判定程度，从结构检查、关系求值逐步深入到局部语义审计。

Progressive Authorization Proof 由三个前后衔接的子方法组成。**Authorization Compilation** 将可信用户请求和工具契约编译为路径无关的 Authorization DAG。该图规定允许产生哪些终端 Effect、关键参数应当如何形成、哪些运行时来源有权补全哪些参数、授权在什么条件下生效，以及每类 Effect 最多可以执行多少次。**Deterministic Runtime Proof** 将真实工具调用和返回绑定到该图，依次检查：当前调用是否产生了用户允许的终端 Effect；运行时新增的读取、搜索或其他中间工具是否确实服务于该 Effect；用户已经指定的参数是否一致；由工具返回动态确定的参数是否按照图中的 Binding 形成。检查结果分为已证明授权、明确冲突和尚未闭合。**Semantic Proof Completion** 把尚未闭合的关系整理为一个具体问题及其最小证据，例如“候选商品 P17 是否满足用户所说的适合出差”。隔离的审计模型据此判断证据支持、证据冲突或证据不足；程序随后校验判断依据，并在必要时补充证据或请求用户确认。三者依次完成授权规范构造、确定性运行时验证和受约束语义判定。

完整流程可以用购物案例串联。用户要求“从指定目录中购买价格低于 500 元且评分最高的相机”，阶段一生成 `search_products → select(price<500) → argmax(rating) → project(product_id) → checkout` 的授权关系，商品 ID 和中间工具顺序留待运行时确定。运行时若 Agent 调用 `send_email`，阶段二在 Effect 层直接拒绝；若调用 `add_to_cart(P17)`，系统根据工具能力契约和对象连接判断它是否为 `checkout(P17)` 的正常中间步骤；若调用 `checkout(P99)`，系统用真实搜索结果执行 DAG，比较授权计算结果与实际参数；若用户改为“购买最适合出差的相机”，有限算子无法判断 P17 是否满足该语义，阶段三审计“P17 是否符合最适合出差”这一原子关系。最终，明显偏离被低成本阻断，正常动态路径由关系证明容忍，真正难以程序化的语义进入受约束审计。

```text
可信用户请求 + 工具／效果契约
              │
              ▼
① Authorization Compilation
   自然语言 → Authorization DAG
   构造可执行授权规范
              │
              ▼
② Deterministic Runtime Proof
   Effect → 动态工具 → 固定参数 → 动态 Binding
   完成结构与关系证明
              │
        ┌─────┼─────┐
      ALLOW  REVIEW  ALERT
              │
              ▼
③ Semantic Proof Completion
   原子问题 → 最小证据 → 三态语义证明
              │
              ▼
       ALLOW / DENY / CONFIRM
```
