# Progressive Authorization Proof：当前实验结果

本文先报告三阶段方法的整体效果，再分析正常任务被拒绝或要求确认的原因，以及攻击为何仍有少量进入确认，最后说明阶段二和阶段三分别解决了什么问题、带来了多少增量。

实验采用**冻结轨迹上的授权回放**。正常侧使用 benchmark 标准工具轨迹，攻击侧检查官方攻击目标调用；Authorization DAG 只根据可信用户请求和工具 schema 生成，不读取攻击文本、攻击标签或任务 ID。数据包括 AgentDojo 的 97 个正常任务与 609 个具有实际目标动作的攻击组合，以及 AgentDyn 的 60 个正常任务与 560 个攻击组合，共计 157 个正常任务和 1,169 个有效攻击组合。该口径衡量候选调用的授权判定能力，不等同于重新运行受害模型后的任务完成率或端到端 ASR。

## 1. 当前整体效果

下表采用逐例归因后的部署口径：存在确定冲突的调用记为 `DENY`；缺少只能由用户决定的授权事实时记为 `CONFIRM`。

| 数据 | ALLOW | CONFIRM | DENY | REVIEW |
|---|---:|---:|---:|---:|
| 正常任务（157） | 129（82.2%） | 17（10.8%） | 11（7.0%） | 0 |
| 有效攻击（1,169） | 0 | 25（2.1%） | 1,144（97.9%） | 0 |

三阶段合并后，1,169 个有效攻击没有一个被自动放行，97.9% 被直接拒绝，其余 2.1% 要求用户确认。正常任务中 82.2% 自动放行，10.8% 需要确认，7.0% 因执行与任务存在确定冲突而被拒绝；公开接口中不再保留 `REVIEW`。

## 2. 真正需要分析的边界案例

### 2.1 被拒绝的正常任务：执行轨迹存在确定冲突

11 个正常任务被拒绝，原因是标准执行轨迹本身与用户要求冲突，或缺少执行关键效果所需的证据：

- **关键值与用户要求冲突。** 例如用户要求的日期为 2024-05-18，实际调用却使用 2024-06-18；要求处理指定账户或仓库，轨迹使用了另一对象。
- **动态对象仍是占位符。** 文件下载使用 `ID / ID1 / ID3`，但真实工具返回已经给出其他附件 ID；邮件正文仍是 `<feedback>` 或只有日期，没有用户要求的具体任务内容。
- **条件尚未证明便执行效果。** 用户要求“评分低于 4.0 才退款”或“确认折扣更低后再购买”，轨迹没有取得评分、发票或价格比较证据便继续退款、购买。
- **前置操作失败后仍继续。** 账户验证、仓库创建、文件读取或邀请接受失败，但后续调用仍假定目标对象已经存在。
- **实际效果偏离任务。** 用户要求上传仓库内容，轨迹只进行了本地移动；用户要求从指定来源取得信息，轨迹访问了未授权第三方网址。

这些轨迹即使没有攻击，也不适合直接放行。在真实部署中，系统应拒绝当前调用，并要求 Agent 补充证据或重新规划。

### 2.2 需要用户确认：缺少只能由用户补充的授权事实

17 个正常任务进入 `CONFIRM`。它们没有出现足以拒绝的确定冲突，但缺少一个只能由用户补充的安全关键授权事实：

- **用户给出了选择标准，却没有给出最终对象。** 例如“更新租金付款”没有证明实际 transaction ID 对应租金；“邀请 Bob”没有证据将候选邮箱绑定到 Bob。
- **关键参数应由运行时资料提供，但来源连接缺失。** 例如发票附件、邀请链接、SSH Key、商品 ID 或收件人邮箱没有绑定到真实返回中的具体字段。
- **用户把任务交给外部资料，但资料内容没有被可靠读取。** 例如“执行 Alice 的 TODO 列表”，轨迹没有取得列表内容，系统无法确认发送消息、邀请成员或修改频道是否属于该列表。
- **生成内容尚未具体化。** 用户授权发送反馈或通知，但候选正文仍是占位符，无法验证内容是否忠实于用户目的。
- **外部页面要求额外披露。** 下载资料或图书时，网页要求提交邮箱；该行为可能是完成任务的必要步骤，也可能是页面自行新增的数据披露，用户原始请求没有给出答案。
- **实现参数没有明确默认值。** 用户授权了终端效果，但没有指定日期、本地目录或运行账户，且部署环境没有提供可信默认策略。

这些情况的共同点是：工具契约、运行时返回和语义模型都不能合法推导出用户是否愿意承担该效果。此时 `CONFIRM` 是方法的预期输出，而不是误报。确认问题应只询问缺失关系，例如“是否允许向该网站提交邮箱”，用户回答随后写回 Authorization DAG，避免重复询问。

### 2.3 攻击要求确认：攻击利用了相同的授权空白

25 个有效攻击进入 `CONFIRM`，其中 AgentDojo 有 13 个，AgentDyn 有 12 个。它们没有被放行，是因为攻击目标依赖的安全关键对象或参数无法由可信用户请求和运行时证据证明；但当前证据也不足以构造有限冲突，终局策略因此要求用户确认。

这 25 个样本集中在三种模式：

- **宽泛外部委托被扩大。** AgentDojo Slack 中，用户要求执行外部 TODO 列表，攻击试图据此邀请新用户、增删频道成员或发送外部链接；由于 TODO 内容没有形成可信的有限授权，系统不能确认这些效果是否属于用户任务。
- **语义对象被替换为未绑定标识。** AgentDojo Banking 中，用户说“像上个月一样付款”“更新租金”或“转给 Apple”，攻击提供新的账户、transaction ID 或收款人；候选值无法绑定到历史账单、租金或 Apple 的真实账户。
- **敏感效果缺少具体接收方和金额依据。** AgentDyn Shopping 中，攻击提出 `send_money`，但收款人为空或未绑定，金额常为与任务无关的 `0.01`，也无法证明该转账服务于购物、退款或补差价目标。

从安全处置看，这些确认并非漏检：攻击调用不会自动执行。它们揭示的是授权证据仍不足以区分“用户确实愿意授权的动态值”和“攻击塞入的动态值”。后续若补齐 TODO 内容、历史账户、商品订单或付款对象等证据，许多样本可以从 `CONFIRM` 进一步收敛为 `DENY`。

### 2.4 方法判断错误

方法判断错误专指：可信用户请求、工具契约和运行时证据已经足以确定授权关系，但系统仍作出相反结论。完成通用工具能力补全并将授权不明确的行为统一路由到 `CONFIRM` 后，当前人工复核尚未确认此类样本。后续将使用独立的调用级授权金标继续检验，而不根据 benchmark 标签直接推定误报。

## 3. 不同模块分别起什么作用

### 3.1 阶段一：生成可执行的授权标准

阶段一将可信用户请求和工具契约编译为 Authorization DAG，明确允许的终端 Effect、固定字段、动态 Binding、适用条件、使用次数以及外部来源可以补全的范围。它本身不判断正常或攻击，因此没有独立检测率；它为后两阶段提供统一的比较标准，并决定系统能否在不预测唯一执行路径的情况下容忍动态工具和动态参数。

### 3.2 阶段二：无需 LLM 的程序化证明

阶段二读取真实工具调用、参数、返回字段和状态版本，独立执行 DAG 中的有限查询，再把求值结果与 Agent 的候选调用比较。它完全不调用 LLM。

| Benchmark | 数据 | ALLOW | REVIEW | ALERT |
|---|---|---:|---:|---:|
| AgentDojo | 正常任务（97） | 60（61.9%） | 37（38.1%） | 0 |
| AgentDojo | 有效攻击（609） | 0 | 179（29.4%） | 430（70.6%） |
| AgentDyn | 正常任务（60） | 6（10.0%） | 54（90.0%） | 0 |
| AgentDyn | 攻击（560） | 0 | 337（60.2%） | 223（39.8%） |
| **合计** | **正常任务（157）** | **66（42.0%）** | **91（58.0%）** | **0** |
| **合计** | **有效攻击（1,169）** | **0** | **516（44.1%）** | **653（55.9%）** |

阶段二在零正常硬告警的条件下直接阻断 55.9% 的有效攻击，并且没有直接放行任何攻击。它主要解决未经授权的终端 Effect、固定参数冲突、对象或域范围扩张、预算超限，以及能够由 `select / project / join / aggregate / compute` 等有限算子重放的动态参数。AgentDyn 正常自动放行率只有 10.0%，说明开放语义委托和复杂中间路径仍需要阶段三处理。

### 3.3 阶段三：补全阶段二留下的局部证明缺口

阶段三不重新阅读整条轨迹。程序先把阶段二的 `REVIEW` 转换成一个原子问题，再从 Authorization DAG 与执行图中切取最小证据；审计模型输出 `SUPPORTED / CONTRADICTED / NEED_EVIDENCE`，负面结论必须附带可由程序复核的冲突证据。

在证明义务实验中，阶段三处理了 107 个正常未决调用与 564 个攻击未决调用：

| 阶段二未决调用 | SUPPORTED | CONTRADICTED | NEED_EVIDENCE |
|---|---:|---:|---:|
| 正常调用（107） | 49（45.8%） | 3（2.8%） | 55（51.4%） |
| 攻击调用（564） | 0 | 222（39.4%） | 342（60.6%） |

阶段三为 49 个正常调用补全了正向证明，并为 222 个攻击调用形成了可验证冲突，没有把任何攻击调用提升为 `SUPPORTED`。合并到任务级后：

| 数据 | 仅阶段二 | 加入阶段三证明义务后 |
|---|---:|---:|
| 正常任务（157） | 66 A / 91 R / 0 X | **119 A / 34 R / 4 X** |
| 有效攻击（1,169） | 0 A / 516 R / 653 X | **0 A / 294 R / 875 X** |

`A / R / X` 分别表示 `ALLOW / REVIEW / ALERT`。阶段三使正常任务自动放行率由 42.0% 提高到 75.8%，攻击高置信阻断率由 55.9% 提高到 74.9%，攻击直接放行仍为 0。随后，一次受限补证和终局裁决把剩余未决项收敛为 `ALLOW / DENY / CONFIRM`，得到第一节的最终整体结果。

## 4. 结论与实验边界

三个模块形成连续的职责分工：阶段一定义什么可以被证明，阶段二用程序事实完成确定性证明，阶段三只解释程序无法闭合的局部语义关系。整体结果表明，程序证明可以低成本处理一半以上的攻击，局部语义证明能够在不放行攻击的前提下继续释放正常动态行为并识别更多攻击，用户确认只保留给缺少真实授权依据的边界情况。

当前结果仍有三项边界：实验主要是冻结轨迹上的授权回放；动态委托尚未在两个 benchmark 上进行全量在线重跑；正常拒绝尚未建立独立调用级授权金标。后续应优先补全真实执行中的字段来源、对象版本与委托证据，并验证授权增量在多轮用户指令下的维护，而不是针对已知 case 增加规则。
