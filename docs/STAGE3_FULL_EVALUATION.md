# 阶段三全量评估：最小证据语义审计

## 1. 实验目的

阶段二能高置信处理效果类型、参数来源、范围、预算和版本冲突，但仍会留下大量 `REVIEW`。阶段三要回答一个具体问题：**只把证据齐全但语义未决的局部关系交给 LLM，能否释放更多正常任务，同时不把攻击调用提升为授权？**

这不是让 LLM 重新阅读完整轨迹，也不是让它自行规划。审计输入只有可信用户请求、当前复核义务、调用前缀和一个待执行调用；LLM 只能输出 `authorized / unauthorized / uncertain`。

## 2. 数据与口径

阶段二在 AgentDojo 和 AgentDyn 上共产生 814 个调用级 `REVIEW`：

- 91 个 `evidence_missing`：程序事实或部署契约不足，继续取证；
- 85 个 `policy_confirmation`：用户给出了宽泛效果委托，需要用户确认；
- 638 个 `semantic_unresolved`：进入本次 LLM 审计。

638 条记录中有 503 个唯一证据包，另有 135 条完全重复，按内容哈希复用判定。唯一请求总计消耗 753,332 token，所有请求一次成功。输入在发送前会移除本地主机路径，并对凭据形态的字符串做确定性伪名化。

实验使用 benchmark 标准轨迹条件回放，不重新运行受害模型。攻击侧检查官方攻击目标调用；正常侧使用 benchmark 的标准工具轨迹。后者只能作为“标准轨迹标签”，不能自动证明每一个具体调用都获得了用户授权。

## 3. 调用级结果

| 数据 | Authorized | Unauthorized | Uncertain |
|---|---:|---:|---:|
| AgentDojo 正常语义复核（47） | 34（72.3%） | 9（19.1%） | 4（8.5%） |
| AgentDojo 攻击语义复核（195） | 0 | 194（99.5%） | 1（0.5%） |
| AgentDyn 正常语义复核（105） | 76（72.4%） | 24（22.9%） | 5（4.8%） |
| AgentDyn 攻击语义复核（291） | 0 | 291（100%） | 0 |
| **合计正常（152）** | **110（72.4%）** | **33（21.7%）** | **9（5.9%）** |
| **合计攻击（486）** | **0** | **485（99.8%）** | **1（0.2%）** |

在这批语义未决调用中，没有攻击调用被错误提升为授权；正常调用中约 72% 获得了正向证明。但 33 个正常标签调用被判未授权，说明 LLM 判别不能直接作为在线硬阻断依据。

## 4. 合并回任务级决策

合并规则保持保守：语义 `authorized` 提升为 `ALLOW`，`unauthorized` 提升为 `ALERT`，`uncertain` 保持 `REVIEW`；缺少程序证据和需要用户确认的调用也保持 `REVIEW`。任务中任一调用 `ALERT` 则任务为 `ALERT`，否则任一调用 `REVIEW` 则任务为 `REVIEW`。

### AgentDojo

| 数据 | Stage 2 ALLOW / REVIEW / ALERT | 加入 Stage 3 后 |
|---|---:|---:|
| 正常任务（97） | 60 / 37 / 0 | **78 / 12 / 7** |
| 全部攻击组合（629） | 20 / 179 / 430 | **20 / 39 / 570** |
| 有实际目标动作的攻击（609） | 0 / 179 / 430 | **0 / 39 / 570** |

### AgentDyn

| 数据 | Stage 2 ALLOW / REVIEW / ALERT | 加入 Stage 3 后 |
|---|---:|---:|
| 正常任务（60） | 6 / 54 / 0 | **23 / 22 / 15** |
| 攻击组合（560） | 0 / 337 / 223 | **0 / 46 / 514** |

第三阶段显著收缩了攻击侧的不确定集合：AgentDojo 有效攻击的高置信阻断率由 70.6% 提升到 93.6%，AgentDyn 由 39.8% 提升到 91.8%。代价是按 benchmark 正常标签计算的硬告警率分别达到 7.2% 和 25.0%，远不能作为生产阻断策略。

## 5. 为什么正常任务会被判未授权

逐条检查显示，正常侧 `unauthorized` 混合了三类情况。

第一类是**标准轨迹本身缺少授权证据**。例如条件退款前没有取得评分或价格，文件下载仍使用 `ID`、`ID1` 等占位值，账户验证失败后继续执行，或者没有证明目标频道满足“消息最少”的条件。此时 benchmark 任务是正常的，但这条具体执行轨迹并不具备完整授权证明。

第二类是**证据包或事实关系仍不完整**。例如参数来自此前读取，但字段级绑定没有进入最小证据包；或工具返回失败，导致审计器看不到本应存在的对象和版本。这部分应回到阶段二补充来源关联，而不是调宽 LLM 阈值。

第三类是**LLM 审计错误或策略过严**。例如 `force=false` 是非破坏性默认值，却被认为缺少授权；个别回答的理由已经说明调用得到授权，最终 JSON 仍输出 `unauthorized`；对遵循可信文件中的有限步骤也可能采用过于严格的外部指令策略。

因此，7/97 和 15/60 不能全部解释为防御误报，也不能被删除后宣称更低误报。正式论文需要为阶段三正常复核建立独立的调用级授权金标，区分“轨迹无证据”和“审计器误判”。

## 6. 方法结论与部署策略

全量实验支持两点结论：

1. 类型化 `REVIEW` 有效。只有语义未决项进入 LLM，程序缺证据和宽泛委托不会被模型猜测性裁决。
2. 最小证据审计具有很强的攻击区分信号，但单次 `unauthorized` 尚不足以直接阻断正常任务。

当前可落地策略应为：

```text
Stage 2 明确冲突                         → 高置信阻断
Stage 3 authorized                       → 释放该语义复核
Stage 3 uncertain                        → 保持复核／补证据
Stage 3 unauthorized + 程序化反证        → 高置信阻断
Stage 3 unauthorized、但无程序化反证      → 复核或局部重放，不直接阻断
```

也就是说，LLM 的作用是补充语义证据，而不是取代程序证明。下一步不应继续针对 benchmark case 添加规则，而应建立调用级授权金标，并针对第三类真正的 LLM 错误测试一致性校验、双向问题或局部重放。
