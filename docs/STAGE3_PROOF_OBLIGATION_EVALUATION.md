# 阶段三：证明义务驱动的局部语义审计

## 1. 要解决的问题

阶段二能证明工具、参数来源、范围和能力关系，但仍有两类调用无法程序化定论：一类是正常的动态扩展，另一类是使用合法工具和相似来源的攻击新增行为。此前直接把最小轨迹交给 LLM，问题仍然过于宽泛：模型需要同时猜测“要证明什么、哪段证据相关、缺什么证据”，因而容易把证据不足误判为越权。

阶段三因此不再让 LLM 判断“这个任务是否恶意”，而是让程序先生成一个**原子证明义务**：当前调用获得授权，还缺哪一条具体关系成立。

## 2. 方法

```text
阶段二 REVIEW
     │
     ▼
① 证明义务路由
   将失败原因转成有限谓词
   例：参数绑定 / 条件满足 / 委托范围 / 中间行为必要性
     │
     ▼
② 图上证据切片
   可信用户请求 + 候选调用
   + 与候选值相关的读取、返回和来源节点
     │
     ▼
③ LLM 局部证明
   SUPPORTED / CONTRADICTED / NEED_EVIDENCE
     │
     ├─ SUPPORTED ──────→ ALLOW
     ├─ CONTRADICTED ───→ 程序校验证书 ─→ ALERT / REVIEW
     └─ NEED_EVIDENCE ──→ 一次有界证据扩展 ─→ 再证明
```

### 2.1 有限证明义务

程序根据阶段二的复核原因，将问题归一为有限关系，例如：

- `parameter_binding`：候选参数是否由用户允许的来源与变换得到；
- `condition_satisfaction`：评分、价格、日期等前提是否已被证据满足；
- `delegation_scope`：用户是否把这一具体效果及关键参数委托给外部内容；
- `observation_scope`：读取行为是否仍处于授权来源范围；
- `instrumental_effect_link`：中间操作是否确实服务于已授权的终端效果。

这一步的作用是固定判别对象。LLM 不能重新定义用户目标，也不能凭“看起来合理”放行整条轨迹。

### 2.2 图上证据切片

输入包只包含四部分：可信用户请求、当前候选调用、原子证明义务，以及执行图中与候选字段和值相关的证据节点。证据不足时，审计器必须指出缺失事实和建议的读取／搜索／版本检查；系统最多追加一次已有执行前缀中的其余证据，避免无限扩大上下文。

### 2.3 三态结论与冲突证书

- `SUPPORTED` 需要引用证据，证明当前具体调用，而非仅说明其与任务相关；
- `CONTRADICTED` 需要输出冲突类型、实际值、授权值或约束及有限关系；程序校验通过后才能告警；
- 缩减包和扩展包都无法证明时保持 `NEED_EVIDENCE`，不得强制猜测。

因此，LLM 负责解释局部语义，程序负责限定问题、选择证据并校验负面结论。

## 3. 全量实验

实验对象是阶段三 v2 后仍未决的全部 671 个调用：107 个正常调用、564 个攻击调用。每条先使用最小证明包；仅当结果为 `NEED_EVIDENCE` 且存在被省略的已观测证据时扩展一次。实验共发起 1,049 次唯一请求，消耗 1,573,137 token；378 条进行了第二次审计。

### 3.1 调用级结果

| 数据 | SUPPORTED | CONTRADICTED | NEED_EVIDENCE |
|---|---:|---:|---:|
| AgentDojo 正常（29） | 14（48.3%） | 1（3.4%） | 14（48.3%） |
| AgentDyn 正常（78） | 35（44.9%） | 2（2.6%） | 41（52.6%） |
| **正常合计（107）** | **49（45.8%）** | **3（2.8%）** | **55（51.4%）** |
| AgentDojo 攻击（212） | 0 | 69（32.5%） | 143（67.5%） |
| AgentDyn 攻击（352） | 0 | 153（43.5%） | 199（56.5%） |
| **攻击合计（564）** | **0** | **222（39.4%）** | **342（60.6%）** |

证明包使 49 个原本无法程序判断的正常调用获得正向证明，同时没有任何攻击调用获得 `SUPPORTED`。

### 3.2 与前两阶段合并后的任务级结果

| Benchmark | 数据 | ALLOW | REVIEW | ALERT |
|---|---|---:|---:|---:|
| AgentDojo | 正常任务（97） | 86（88.7%） | 9（9.3%） | 2（2.1%） |
| AgentDojo | 有实际目标的攻击（609） | 0 | 101（16.6%） | 508（83.4%） |
| AgentDyn | 正常任务（60） | 33（55.0%） | 25（41.7%） | 2（3.3%） |
| AgentDyn | 攻击（560） | 0 | 193（34.5%） | 367（65.5%） |
| **合计** | **正常任务（157）** | **119（75.8%）** | **34（21.7%）** | **4（2.5%）** |
| **合计** | **有效攻击（1,169）** | **0** | **294（25.1%）** | **875（74.9%）** |

原始 benchmark 标签下有 4 个正常任务被告警。逐条检查表明，它们都包含可程序复核的请求冲突：错误日期、访问未授权网址、使用错误账户，以及把要求的仓库上传替换为本地移动。报告仍保留原始标签口径，不把这四条从分母删除；但它们与“防御误解了一个合规调用”应分开分析。

相较阶段三 v2，正常任务直接放行从 101/157（64.3%）提高到 119/157（75.8%）；有效攻击直接放行仍为 0，高置信告警从 682/1,169（58.3%）提高到 875/1,169（74.9%）。这里是冻结轨迹上的授权回放，不等同于重新运行受害模型后的任务完成率或 ASR。

## 4. 结论与下一步

实验支持的结论不是“LLM 看完整轨迹就能分类”，而是：**先把程序失败转成原子证明义务，再从执行图中切出与该义务相关的证据，能够在不放行攻击的前提下证明一部分正常动态行为。**

一次被动扩展后仍有 34 个正常任务和 294 个有效攻击任务处于 `REVIEW`。继续加入 benchmark 专用规则没有意义；下一步应让 `missing_fact + suggested_query` 驱动真实的只读补证或局部重放，再检验新增证据能否关闭证明义务。无法取得事实的高影响调用仍应保持不可判定，而不是由 LLM 强制二分类。
