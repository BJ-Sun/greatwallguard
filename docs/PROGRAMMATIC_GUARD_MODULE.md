# GreatWallGuard Programmatic Core v0.1

## 1. 它解决什么问题

该模块在 Agent 调用工具之前，判断当前调用是否能由截至此刻的可信用户指令授权。它不是完整的攻击分类器，而是低成本的第一层运行时检查：明确符合用户授权的调用直接放行，明确缺少授权或违反显式参数的调用告警，无法仅靠程序事实判断的调用进入语义审计。

模块不读取攻击标签、case oracle、最终任务结果或未来工具返回，因此可以从离线实验迁移到真实 Agent 的在线工具网关。

## 2. 固定算法

```text
可信用户消息
    ↓  保守提取
有界授权账本：操作 + 关键参数 + 使用次数 + 原文证据
    ↓
Agent 提议工具调用
    ↓  调用前匹配
ALLOW / ALERT / REVIEW
    ↓
工具成功后才消费对应授权
```

三个判定具有固定含义：

- `allow`：调用与一条尚未消费的明确授权一致；
- `alert`：没有对应授权，或关键参数明确冲突；
- `review`：工具影响未知，或操作虽可能合理但参数、对象、来源仍未绑定。

算法遵守四条不变量：只有可信用户消息能增加授权；未知工具默认进入 `review`；授权在工具成功后才消费；不确定性不得自动转成授权。

## 3. 程序接口

安装本仓库后，Agent 运行时只需在三个位置调用模块：

```python
from greatwallguard import ProgrammaticAuthorizationGuard

guard = ProgrammaticAuthorizationGuard()

# 收到经过身份验证的用户消息时
guard.on_user_message(user_text, turn=turn, trusted=True)

# 工具真正执行前
decision = guard.before_tool_call(
    tool_name,
    arguments,
    turn=turn,
    call_id=call_id,
)

# 工具返回后；失败不会消费授权
guard.after_tool_result(call_id, succeeded=not tool_error)
```

状态可以用 `export_state()` 导出为 JSON，并用 `from_state()` 恢复。这样多轮任务在进程重启后仍能保留已授权、已消费和待确认的调用。

## 4. 固定部分与适配部分

跨 benchmark 不应修改判定流程、三态语义、账本生命周期或成功后消费规则。需要适配的只有两类输入：

1. 将目标 Agent 的消息和工具事件转换为上述三个接口调用；
2. 为新工具补充有限的 effect/关键参数契约，并扩展用户表达的提取规则。

因此，在 AgentDojo、AgentDyn 或其他 benchmark 上出现差异时，首先记录为“事件适配缺失”“工具契约缺失”“意图提取缺失”或“确需语义判断”，而不是直接修改核心判定逻辑迎合结果。

## 5. 当前验证

模块化后重新回放了冻结的 570 条轨迹、5,674 次工具调用。新模块与原 V1 实验逐调用完全一致，差异为 0；同时新增了公开接口、单次授权消费、未知工具降级、非可信消息隔离以及状态序列化测试。

当前结果仍保持：258 条具有可检查目标调用的攻击中，63 条产生高置信告警，195 条进入复核；265 条正常轨迹没有高置信误报，其中 79 条进入复核。该结果说明模块已适合作为跨 benchmark 的固定算法基础，但不能把 `review` 当作自动阻断，否则正常任务成功率仍会受到明显影响。

## 6. 下一阶段的实验纪律

下一 benchmark 先保持核心模块不变，按以下顺序推进：

```text
接入事件适配器
→ 运行正常与攻击轨迹
→ 按失败原因归类
→ 只补充可泛化的工具契约或提取规则
→ 对剩余 REVIEW 设计来源／版本证据或局部 LLM 审计
```

只有当新 benchmark 暴露出无法由现有三态语义表达的机制性问题时，才升级核心算法版本。
