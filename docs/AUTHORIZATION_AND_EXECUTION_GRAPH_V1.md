# GreatWallGuard：跨任务状态版本的效果授权

> 这是防御方法的研究主线，不把尚未验证的判别能力写成实验结论。现有代码和实验数字见[原型记录](PROTOTYPE_NOTES.md)。

## 1. 问题：持久状态让越权跨越任务边界

Agent 执行任务时不仅调用工具，还会持续改写记忆、文件和环境。这些改写既是当前任务的结果，也是后续任务的输入。由此出现一个单步审计容易忽略的安全边界：用户授权了后续操作所用的工具和来源，并不意味着 Agent 在先前任务中有权生成该来源的当前版本。攻击可以先影响一次看似正常的资料整理或状态更新，再由后续正常操作使用留下的状态；最终动作无需出现额外工具或异常路径。

[仓库中的真实案例](../../openclaw-longrange-manual-lab/dataset/model-output-integrity/curated/double-success/user_task_26/MOI-T1-V24-document-email-project-delayed/case.json)展示了这条路径的关键环节。Agent 完成用户要求的项目回执，把外部项目资料写入 `MEMORY.md`，在后续交接中回读记忆，却将 `PROJECT_STATUS.md` 的“正式风险状态”从 `pending` 更新为 `resolved`，最终报告也沿用了错误状态。问题不在于写了项目文件——维护交接记录本就是正常工作——而在于“本轮处置完成”的资料被提升为“正式风险已解决”的持久状态。[完整时间线](../../openclaw-longrange-manual-lab/docs/attack-targets/state-provenance-motivation.md)另有记录。

这揭示了本文要处理的矛盾：**只检查最终工具和参数来源，看不到来源版本是如何形成的；把外部资料参与或文件写入一概视作风险，又会阻碍正常任务。** 安全判断必须同时回答两个问题：某次状态变化是否属于当时用户允许的更新，以及后来产生的效果是否依赖这个版本。我们的目标是让授权约束随用户任务变化，并让状态版本的形成与后续使用保持可追溯，而不是预测一条唯一的正常工具轨迹。

## 2. 相关工作：各自解决了什么，还留下什么

**CaMeL [1]：控制流与数据流隔离。** 它从可信用户请求生成执行程序，让外部资料只提供数据，并用能力标签和安全策略约束参数的流向。其效果取决于策略是否表达了当前任务的限制：同一文件编辑工具，在不同任务中可修改的字段可能不同。CaMeL 的策略语言可以表达细粒度条件，但实际部署既要接入其执行架构，也要为不同任务语境提供足够准确的策略；不能假定一份按工具配置的通用规则会自动覆盖这些差异。**因此，策略执行本身不是缺口；难点是让权限随具体任务变化，而不要求预先穷举所有正常与异常的字段修改。**

**AttriGuard [2]：判断调用是否受外部内容驱动。** 它弱化工具返回中的控制信号并做影子重放，观察拟议调用是否仍会出现，无需读取模型内部状态。当用户要求依据外部资料选择收件人时，合法调用本来就依赖资料；论文也把用户明确授权资料完全决定关键参数的情况列为非目标。长任务中，正常的调用顺序、批处理与参数格式变化还可能使重放出现差异。**因此，调用依赖外部资料只是因果事实，不是越权结论；重放不能独自区分正常委托与恶意改写。**

**AuthGraph [3]：核对工具步骤和逐参数来源。** 它只用用户请求与工具目录生成授权图，再将实际调用及关键参数的来源与之对齐；辅助步骤判断和受限重规划容纳部分正常执行变化。它能发现从错误工具结果中取参数，却将用户指定的来源本身已被篡改、但工具和参数来源仍符合授权图的情况排除在评估之外。我们的目标场景中，文件起初可信，之后由 Agent 在先前任务里改写，再被当作指定来源读取。**因此，仅验证“值确实来自用户指定的文件”，不能确定 Agent 是否获准生成该文件的当前版本。**

**PAuth [4]：核对具体操作数是否符合任务。** 它把用户任务转为服务端可检查的约束，以服务端证明连接参数、权威上游值和计算过程，不要求固定 Agent 的完整工具轨迹。其可信链条以服务器参与、权威服务器如实提供自身数据为前提；Agent 工作区内反复修改的文件没有天然的权威服务为每个版本担保。**因此，它能验证有权威来源的参数计算，却不能直接为本地中间状态的每次改写提供授权依据。**

**AGATE [5]：跨步记录授权、来源与重复请求。** 它结合操作者声明、主机批准、来源登记和请求账本，也区分预存资料与 Agent 写入；受保护记忆的写入可进入人工审批。它的授权依据主要来自操作者预设的工具、目标权限与主机批准。对于普通工作文件，“由 Agent 写入”既可能是正常编辑，也可能是攻击诱导；如果不为每种任务预设字段级策略或逐次审批，来源标签本身无法区分两者。**因此，跨步记录已被解决一部分，尚需把具体用户任务的修改范围与记录到的状态变化对齐。**

**综合来看，缺的不是另一种工具调用记录，而是任务语境下对状态变化的授权。** 预设策略可以执行明确的边界，重放可以显示外部内容是否影响调用，来源检查可以证明参数从哪里读出；但这些事实都不自动说明 Agent 是否有权在先前任务中改写那个来源。正常任务又确实需要修改文件，所以“一写就拦”同样不成立。我们据此只研究一个明确问题：后续任务允许从某状态读取值时，如何判断此前形成的新版本及其后续用途是否仍在授权范围内；其增益必须相对于明确策略和即时写入检查来验证。

## 3. 核心机制：状态版本授权

我们不预测 Agent 应走哪条工具轨迹，而是给每个可被后续复用的状态版本保留一条授权记录。判定对象不是“是否调用过某工具”或“是否写过某文件”，而是**某个被实际使用的字段值，是经哪些修改形成的；这些修改在发生时是否获准**。这使跨步检测成为一次从效果回溯到状态形成过程的检查，而不是反复扫描完整长上下文。

```text
可信用户指令 A ──授予可做的状态修改──> 写入 W ──生成──> 版本 V
                    │                                      │
后续用户指令 B ──授予可产生的效果───────────────────────┐   │
                                                     ▼   ▼
                                               使用 V 的实际效果 E
```

新用户指令可以改变此后的授权，但不会自动追认历史写入。正常任务可以通过不同工具顺序到达同一效果，也可以多次编辑文件；只需检查最终使用的关键字段所对应的有效版本。若某字段后来被独立、合法地改正，不应继续用已被覆盖的旧值判定当前效果。这一点必须通过实际版本和回读证据确认，不能仅因两个文本相似就声称存在因果链。

## 4. 拟议方法：每次状态变化都进入同一个核验循环

方法只维护三类持续更新的记录。**授权记录**来自可信用户消息、工具效果定义和明确可用的业务规则，写明当前任务允许修改的对象与字段、允许外部资料填充哪些值、允许产生什么效果，并保留授权原句。**版本记录**由工具事件和前后快照产生，写明实际修改了什么、形成哪个新版本、曾读取哪些可见来源，以及证据强弱。**使用记录**连接拟执行效果的关键参数或输出字段与实际读取的状态版本。它们不是三种检测器，而是一条“授权写入 → 形成版本 → 使用版本”的运行时链。

```text
授权：任务轮次、允许的效果/修改对象/字段、可委托的取值来源、依据原句
版本：对象与字段、父版本、前后值或差异、写入事件、对应授权或待审状态
使用：拟产生的效果、关键参数或输出字段、读取的版本、关联证据
```

```text
收到用户消息     更新授权；含糊授权保留为待审
观察到状态写入   生成新版本；明确越权可立即告警，其余保留形成证据
准备产生效果     只回溯本次实际使用的关键字段及其有效版本
作出判定         修改与使用均获准 → 放行
                 存在明确越权且仍影响本次效果 → 阻断
                 授权含糊或版本关联不足 → 审计
```

这一循环有两条边界。其一，外部资料可以提供用户委托它提供的任务数据，但不能自行扩大用户许可；“从资料中提取本轮进展”不自动包含“依据资料改变正式风险状态”。其二，不能把数据集 oracle 当作防御方事前已知的规则：如果用户消息、可信初始状态和业务规则都不足以确定状态更新权限，就只能审计，不能宣称自动证明越权。语义模型只处理这类有具体争议的授权或值关联，输入是用户原句和相关版本片段，而非全部历史轨迹；它的判断也不能反过来伪造缺失的写入或回读证据。

当前原型已有[用户授权账本](../src/greatwallguard/authorization_rules.py)、[非生成式执行图](../src/greatwallguard/native_openclaw_graph.py)及[逐事件审计接口](../src/greatwallguard/online_auditor.py)：能够按用户消息更新效果级许可，并从真实 OpenClaw 事件记录文件级变化与参数候选来源。**尚未实现的是这条机制的核心连接**：可核查的字段级版本差异、写入时的授权绑定，以及“当前效果使用了哪个版本”的可靠关联。因此，本文提出的是待完成的状态版本授权方法，而不是已验证有效的线上防御。

第一阶段针对良性用户任务及运行中进入的低信任外部内容，假设工作区存在可信初始版本，且相关写入与回读可观察。后续真实用户消息可以修改授权；无可信初始版本的预先投毒、不可观测修改及用户直接要求有害行为，不在这一阶段的保证范围内。

## 5. 下一步：先完成一条可判定的闭环，再扩展难例

第一步只围绕一个可解析的持久文件及少数关键字段，完成“用户授权 → 实际写入 → 字段版本 → 后续回读 → 拟执行效果”的连续记录。以 V24 为状态改写种子，但不把它的正常回执误当作污染后的最终效果；需要在同一个工作区继续运行后续任务，取得真正的回读与效果证据。完成标准是：每个用于判定的字段变化、回读和效果参数都能定位到原生事件或快照，缺失的连接明确标为未知。

第二步构造配对对照，而不先扩充大批攻击变体：相同初始状态下，分别运行保持原状态的正常交接、得到真实用户授权且有正式依据的合法状态升级，以及攻击推动的状态升级；再加入正常的重复读写和不同执行顺序。先单独评估授权记录是否准确，再评估版本链是否完整，最后在相同审计预算下测量效果判定、正常任务误报和开销，避免把提取错误误认为图失效。

第三步只针对闭环中暴露出的难例深化方法。核心对照是“写入时立即检查”与“最终只检查工具和参数来源”：若它们已经能以相同误报拦住攻击，版本回溯没有独立价值；若写入时含义未定、后续使用才显露越权，才进一步研究如何判定委托范围、版本传播与合法覆盖。完整轨迹 LLM 审计及移除版本连接的消融用于检验：结构化回溯是否真的减少误报或审计成本，而非仅增加实现复杂度。现有实验细节与边界见[原型记录](PROTOTYPE_NOTES.md)。
