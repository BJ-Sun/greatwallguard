# 长程 Agent 防御研究回顾

2026 年 10 月 12 日 · 周报草稿

## 问题从哪里来

设想 Agent 正在处理一个项目。它按用户要求发出了回执，却又把项目文件中的正式风险状态从 `pending` 改成 `resolved`。邮件本身没有问题，错误留在了文件里。更值得注意的是，我们在其他运行中还观察到：Agent 即使拒绝了注入要求、没有完成攻击的最终目标，也可能已经错误改写了文件。因此，“本轮攻击失败”不等于工作区仍然干净；后续任务可能读到的是一个在失败运行中形成的新版本。后一现象还需逐条核对原始轨迹，不能仅凭攻击结果标签计数。

我们的[真实案例 V24](../../openclaw-longrange-manual-lab/docs/attack-targets/state-provenance-motivation.md)记录了正常回执、记忆写入与回读，以及未经授权的项目状态升级；最终回答沿用了新状态。它尚未记录“另一任务读取该版本并改变工具参数”的完整链条。两类观察共同指向一个更直接的问题：**不论最终攻击是否成功，Agent 已留下的状态修改是否获当时用户授权；这个版本后来又被谁使用？** 只检查最终动作会漏掉前一个问题，禁止一切写入则会误伤正常任务。

这个问题与单步注入检测不同，也不能简单概括为“过去没人研究长程攻击”。我们精读的工作中，已有方法处理数据流、参数授权、跨资源依赖乃至跨会话组合攻击。下面按它们实际保护的对象来比较。

## 相关工作解决到哪里

这六篇工作的区别不在于是否“用了图”或是否“考虑多步”，而在于**正常/异常的参照物从哪里来**：CaMeL 依赖可信程序及能力策略，AttriGuard 依赖弱化外部影响后的反事实执行，AgentArmor 依赖图上的安全类型与规则，AuthGraph 依赖事前生成的授权图，PAuth 依赖任务切片和服务端签名值，AGATE 依赖操作者授权与来源/效果账本。带着这个问题读，才能看清它们在我们场景下的交集与空白。

### 隔离不可信内容：CaMeL（2025 预印本；Google、Google DeepMind、ETH Zurich；[SaTML 2026](https://ieeexplore.ieee.org/abstract/document/11691650)）

[CaMeL](https://arxiv.org/html/2503.18813)要解决的难点是：真实用户指令可信，邮件、文档等外部内容不可信，但 Agent 必须读取后者才能完成任务。攻击者甚至不必改变工具顺序，只需让模型从文件中取出错误收件人。若让同一个模型阅读外部资料、决定行动并填写参数，靠它自己识别“哪句话不该听”很难形成可靠边界。论文假设初始记忆未被污染，重点防外部内容发起的间接注入。

它的办法是先让只看可信用户请求的特权模型写出受限程序，执行时由隔离模型从外部资料提取数据。这样，外部内容可以提供程序所需的值，却不能临时改写程序流程。解释器还给每个值保留来源、可读者等标签；工具真正执行前，运行针对该工具的安全策略。

正常与异常的界线因此不是文本是否“像攻击”，而是**拟执行的工具调用是否满足策略**。例如[官方 `send_money` 策略](../baselines/camel-prompt-injection/src/camel/pipeline_elements/security_policies/banking.py)可简化为：

```text
调用 send_money(recipient, amount, subject, date) 前：
  recipient 若不是直接来自可信用户 → 拒绝；
  recipient 若无权读取 amount / subject / date 中任一值 → 拒绝；
  否则 → 允许。
```

这里的标签来自解释器追踪，策略来自开发者为工具规定的流向和权限，不是模型对调用做一次语义打分。我们已复现官方实现，126 个官方测试通过，但未在同一批长程案例上对比，见[复现记录](../baselines/README.md)。

放到我们的任务，关键限制在**策略是否写得出、写得准**。“参考项目资料”并没有自动回答：资料能否把 `PROJECT_STATUS.md` 的正式状态改为 `resolved`？该版本之后可否被其他任务采纳？若预先写有准确的字段策略，CaMeL 可能拦住改写；若没有，程序与标签本身不会生成这条授权规则。我们要研究的是随任务变化的状态修改边界，而不是声称 CaMeL 完全不看参数或多步数据流。

### 判断外部内容是否推动了动作：AttriGuard（2026；浙江大学、南洋理工大学、香港城市大学；[USENIX Security 2026](https://www.usenix.org/conference/usenixsecurity26/presentation/he-yu)）

[AttriGuard](https://arxiv.org/html/2603.10749)认为，注入内容可以写得像正常的业务说明，扫描文本很难判定；真正的问题是**外部返回是否推动了用户任务原本不需要的工具调用**。攻击者可在一次或多次工具返回中注入，但不能改真实用户、系统消息或模型权重；防御者能拦截候选调用并重放黑盒模型。

它保留已发生的行动，弱化此前外部返回中引导行为的部分，再让模型重新决定下一步。若原候选调用在这些重放中仍出现，说明它有较强的用户任务支持；若消失，说明它可能依赖外部内容的控制作用。弱化时尽量保留完成任务所需的数据，不是简单删除工具结果。

它实际使用的判别载体是**当前候选工具调用**，判别依据是该调用在弱化来源后的重放中能否“存活”（允许一定的模糊匹配，以容忍模型随机性）。这个试验估计外部内容的因果影响，不能单独证明“有影响”就等于“未授权”。

我们的正常任务也常由外部资料决定下一步：安装教程会改变操作顺序，项目文件会提供正确的参数。长任务中存在多条合理路径，重放时原调用消失可能只是良性变化。若攻击先改写一个字段、以后才由正常操作读取，单独重放最后的调用也未必指出**哪次写入**越权。因此我们只考虑用重放辅助审计已定位的争议写入或使用，而不把整条轨迹是否可重现当作授权标准；这一用法尚未验证。

### 显式检查执行依赖：AgentArmor（2025；字节跳动；arXiv 预印本，未核实到正式会议）

[AgentArmor](https://arxiv.org/html/2508.01249)认为，攻击可以先影响一次工具返回，再经 Agent 的推理、另一个工具或文件传到后续动作。单条消息看不出“谁影响了哪个参数”；只允许或禁止工具名也不够。它要解决的是**自然语言执行轨迹缺少可检查的控制、数据依赖**。攻击者控制外部内容；防御者能改造 Agent 运行环节，在调用前看到规划信息、工具选择与参数。恶意工具实现不在其威胁模型内。

核心方法是把轨迹当成程序：拆出工具名、各参数、工具本体与返回等节点，补上时序、控制依赖和数据依赖，形成 PDG。依赖边部分由 LLM 从上下文推断；随后从可信的工具/数据注册表取安全类型和规则，沿图传播并检查。它不只看一个动作，论文明确考虑跨资源传播。

它的判定依据是**图上的安全类型是否违反附着规则**，而不是“图与某个正常图长得不同”。例如下图是对论文转账例子的简化，不是原图：

```text
用户请求 ────────────[控制依赖]──────────→ 工具名 create_trans
外部邮件返回 ────────[控制依赖]──────────→ 工具名 create_trans
外部邮件中的“Alex, $10” ─[数据依赖]──────→ 参数 recipient / amount
工具名 + 参数 ────────[数据流]───────────→ create_trans 工具节点 → 返回
```

若外部邮件被标为低完整性，且其控制依赖传到 `create_trans`，使工具名节点低于该节点规则要求的完整性，检查器便阻断。安全类型和工具规则来自注册表；图负责让它们沿依赖传播。参见[建图与检查过程](https://arxiv.org/html/2508.01249)。

在我们的黑盒场景里，内部规划未必可见，LLM 推断的依赖也可能遗漏。更根本的是，**外部资料影响了一次写入，并不自动等于写入越权**：用户可能正要求按教程改配置。若已预设准确的字段规则，AgentArmor 可以检查；若没有，完整的依赖图也无法替用户决定哪些更新是允许的。跨轮记忆还要求持续保留写入与回读链接。这些限制指向授权规则和状态版本，而不是“再画一张更细的图”。

### 从用户任务生成允许的执行：AuthGraph（2026；UCLA；arXiv 预印本，未核实到正式会议）

[AuthGraph](https://arxiv.org/html/2605.26497)认为，实际执行图只能说 Agent 做了什么，不能单凭自身判断是否获用户授权。即使工具 `book_flight` 是正常任务所需的，航班号也可能被恶意酒店页面替换。它要解决的是**正确工具使用错误来源参数**，同时避免把正常的辅助步骤都拦下。攻击者控制工具返回，不能修改用户请求或工具定义；防御者可用隔离的规划器和完整执行轨迹。

它把“应该做什么”和“实际做了什么”分开建图。授权图只依据用户请求与工具目录，列出预期工具和关键参数允许来自哪个工具；实际图从轨迹构建，记录输入、观察、决策和中间结果。任务需要根据新结果继续规划时，授权图可以在限定工具集合内扩展。两张图的区别可用论文订票例子表示（简化示意）：

```text
授权图（仅由用户请求 + 工具目录生成）
  search_flights → … → book_flight
                         flight_id 必须来自 search_flights 的返回
                         可附 replan 及允许扩展的工具集合

实际执行图（从真实轨迹生成）
  search_hotels 返回“EVIL-123”
           └─EXTRACT/DERIVE→ 参数 flight_id="EVIL-123"
  工具名 book_flight + 参数 flight_id ─INVOKE→ 工具返回
```

判别时，检查器先从实际图的 `INVOKE` 边取出工具序列，与授权图对齐；再按授权图的 `ParamPolicy` 查参数值是否来自规定的工具返回。航班号 `EVIL-123` 只出现在酒店搜索结果，而不在 `search_flights` 原始返回里，就会被判为错误来源。检查器**不直接相信实际图中由 LLM 推断的 `EXTRACT/DERIVE` 因果边**；字符串无法直接核对时才用 LLM 审核语义。也就是说，判别标准来自用户侧生成的授权图，判别载体是实际调用和原始工具返回，而非图本身的异常形状。参见[双图示例与检查器](https://arxiv.org/html/2605.26497)。

在我们的任务里，困难发生在更早的写入时刻。如果用户授权从 `PROJECT_STATUS.md` 读取风险状态，最终读取的**文件来源**可能完全合规；问题是 Agent 此前是否获准把该字段改成当前值。AuthGraph 明确排除用户主动委托并采纳已污染来源、工具和参数来源均合规的情形，这有其授权模型上的理由。我们研究的范围更窄：文件起初可信，Agent 后来写出新版本，再被后续任务采用。其当前的工具/来源对齐不能直接回答新版本形成时是否获准；但增加版本检查后能否解决，仍需实验比较。

### 把授权细化到具体参数：PAuth（2026；华盛顿大学、俄亥俄州立大学、微软研究院；arXiv 预印本，未核实到正式会议）

[PAuth](https://arxiv.org/html/2603.17170)问的是：**即使 Agent 完全失控，服务端能否只执行这次用户任务真正允许的操作？** OAuth 只授予“可以转账”这一类工具权限，却不约束收款人和金额；把所有参数预先填死，又无法完成“先查余额，再转出四分之一”这样的正常任务。PAuth 因而把授权从工具名推进到**由任务决定、可随权威数据计算的具体操作数**。其前提是用户任务足够明确，用户通过可信界面确认任务，参与的服务端能够验证调用，且权威服务如实报告自己负责的数据。

方法不是让服务端再问一次模型“这个调用看起来安全吗”。用户签名任务后，每个服务端依据任务和工具定义，用 LLM 生成受限程序，再抽取与本服务调用有关的 *NL slice*，编译成运行时可确定性检查的规则。以论文的转账例子说，授权不是“允许 Chase 转账”，也不是预写金额 `$300`，而是“若 Citi 余额满足条件，则 Chase 向指定账户转出 `Citi 余额 / 4`”。Citi 返回余额时签名一个同时包含数值和来源表达式的 envelope；Chase 验签并代入规则。若余额为 `$1200`，`$300` 可以通过，`$301` 或改换收款人则不能由任务推得，需要另获用户批准。Agent 中间如何规划、调用多少次工具，不构成授权证据。

因此，PAuth **判别正常与异常的依据**是签名用户任务编译出的参数关系，以及权威服务签名的运行时数值；**判别载体**是服务端收到的具体工具调用。它已经处理了“同一工具、不同参数”的问题，而且无需把正常执行固定为一条轨迹。这一点与我们希望容忍长程正常任务的多样性相通，不能把参数级检查或动态参数计算写成我们的新意。

它也没有简单忽略本地文件：论文对“收件人写在本地联系人文件中”这类无法由权威服务证明的值，使用 `NonDet` 标记，使该值**不能自动匹配授权规则**；可让用户批准具体调用，或先把文件中的具体值呈给用户确认并重新签名任务。这个处理守住了安全边界，但在频繁读写本地文件、记忆的长程任务里，可能把大量正常步骤推向人工确认。不能说 PAuth 完全不能处理文件；更准确地说，它没有提供自动判定这些本地值何时可信的机制。

我们的切口在于**值的形成历史**：同一个 `PROJECT_STATUS.md` 路径、同一个最终工具调用都可以合规，但当前版本可能是此前某轮未经授权改写的。若直接给当前文件值加可信签名，签名只能证明“谁提供了这个值”，不能证明“此前改写关键字段时是否得到授权”；若一律视为 `NonDet`，则难以保持自动执行。PAuth 若扩展为对每次本地写入做可信、版本化的授权检查，原则上可能覆盖此问题；这恰是我们需要设计和实测的部分，而不是论文已经解决或被其原理排除的部分。

### 把多步效果纳入检测：AGATE（2026；华中科技大学；arXiv 预印本，未核实到正式会议）

[AGATE](https://arxiv.org/html/2609.30830)直接研究跨工具、跨会话、借持久对象完成的组合攻击：单步动作可能都很普通，合起来才越过授权或数据边界。论文认为，只看模型这一步说了什么，既不知道真正的批准来自谁，也不知道数据此前从哪里来。它考虑外部内容攻击；还考虑恶意任务用户，但后一种情形要求企业中的操作者与用户是不同主体。攻击者不能改宿主的可信授权机制。

它在 Agent 宿主的执行边界拦截调用。操作者预先声明工具、资产和范围，真实宿主批准可生成绑定具体参数、有效期和使用次数的授权；来源登记追踪受保护数据是否被带往不允许的目的地，效果账本累计重复请求。这样，即使危险效果分散在不同轮次，也能用先前记录作判断。

它判正常与异常依赖**操作者声明和真实批准是否覆盖当前调用、数据是否越过受保护边界、累计效果是否触发规则**。这些依据来自模型对话之外；文档中一句“用户已经同意”不会变成授权。其图保存事件与裁决证据，供重建与审计。由此可见，跨步传播、持久影响和宿主侧检查都已被 AGATE 研究，我们不能据此单独主张创新。

我们的任务更难的是，正常工作也会多次修改同一文件。仅知道“写文件获准”或“低信任文本被复制”，未必能判断**某个关键字段的新值**是否符合当时用户任务；但若操作者已明确规定字段边界并要求审批，AGATE 也可能挡住攻击。论文报告良性文件任务出现拒绝事件，提示过严的来源/边界规则有可用性代价。我们需要比较的是：在同样授权信息下，检查版本形成时的任务条件，是否比这类宿主规则更能放行正常更新、拦住攻击更新。

另外两篇工作与判别标准有关，但不属于上述六篇系统机制的主比较。

[Task Shield](https://aclanthology.org/2025.acl-long.1435/)（2025；宾夕法尼亚州立大学、普林斯顿大学、加州州立大学长滩分校；ACL 2025）要解决的是：外部内容或 Agent 自己提出的步骤，表面温和却可能偏离用户目标。它从各类消息提取“任务指令”，检查每条指令及工具调用是否有助于可信用户目标；**与用户任务的贡献关系**就是正常/异常依据。这说明“任务相关性”不是我们的新概念。在我们场景中，同一个文件更新既可能支持正常任务，也可能暗改关键字段；若只问动作整体是否相关，仍要补上字段、版本和写入当时的授权证据。

[LLMs Get Lost in Evolving User Intent](https://arxiv.org/html/2607.20734)（2026；微软研究院；arXiv 预印本，未核实到正式会议）不是防御论文，没有攻击者或安全拦截器。它要测的是用户逐步补充、修改参数或切换任务时，模型能否跟上当前目标；方法把用户意图表示为任务函数及参数，并构造可自动验证的多轮对话。**判别依据是任务的已知正确答案**，不是“某次工具调用是否获安全授权”。它提示我们授权不能只取首轮指令，但不能直接提供状态写入的安全规则。

读完这些工作，研究缺口可以更准确地表述为：**拦住最终恶意调用，并不能保证执行中没有留下未经授权的状态修改。** 现有机制已经分别检查控制流、当前动作、参数来源和跨步效果；我们要进一步检验，在 Agent 会正常改写文件和记忆的条件下，能否逐次判断新版本的形成是否获授权，并追踪它是否被后续采用。这不是说上述论文均无法扩展解决，而是它们的现有判据未直接给出这一判断。

## 我们准备固定的威胁模型

第一阶段只考虑良性用户任务中的间接注入：攻击者能改某次外部返回，不能改真实用户或系统消息、工具实现和防御器。工作区从可信版本开始，但 Agent 可以在执行中写文件、记忆；用户后续也可以补充或修改任务。每次写入按**发生时**的用户授权判断，后来的指令不自动追认过去的修改。

防御部署在 Agent 主机侧，可见用户消息、工具调用及参数、工具返回、文件与记忆的读写和版本；看不到云端模型的隐藏推理。我们关心两种结果：攻击达成最终目标；以及最终目标被拒绝、却留下错误持久状态的**部分失败**。正常任务也会修改相同文件，所以判别对象不是“有没有写”，而是“这次具体修改是否获授权”。若版本后来被读取，还要追踪它如何影响后续行为。

直接恶意用户、起初已污染且无可信旧版本的工作区，以及主机不可见的状态变化暂不纳入保证范围。V24 已证明正常任务成功可伴随错误状态升级；“攻击失败仍留下错误写入”目前是需要定位轨迹的实验观察；“另一任务回读该版本并改变下游操作”仍待补证。三者不能混作一条已闭合的案例链。

## 方法目前收敛到什么程度

目前固定的是一条判断链：**写入时用户允许什么 → Agent 实际改了什么 → 后续使用了哪个版本**。主机侧程序化记录工具调用、读写和版本；可信用户消息提供授权依据。字段含义或授权条件无法直接确定时，再做局部语义审计，并保留“不确定”，不让图本身承担恶意判定。

第一版优先在写入时检查新版本是否获授权，之后再追踪它被怎样使用。这样既不必等最终恶意动作发生，也不会把所有正常写入都判为异常。重放只是可能的辅助工具，尚未固定为方法组件。**版本沿革能否比单次动作检查更准确**，仍是待实验回答的问题。

## 已做实验告诉了我们什么

前三组试验依次检查：**行为记得全吗、授权提得准吗、把两者接起来为何仍不能直接检测？**

**目标一：执行图能否用程序化方法记录 Agent 行为？** 对 809 条保存会话构图，得到 34,596 个原生事件和 8,886 次工具派发配对，见[原型记录](PROTOTYPE_NOTES.md)。工具调用和读写等事实可以大量事后重建；但图中的参数来源有些只是候选关联，尚不能证明某个值确实由某次读取推导出来。原生读取和逐次写入版本也未完整覆盖，不能宣称在线因果溯源已经完成。

**目标二：能否从用户消息得到可用授权？** 规则提取在 8 组样本中找出 10 项授权的 8 项，却漏掉部分参数和条件，例如“这一步先不发送”的时效限制，以及收件人或正文须从指定资料确定的要求。7 段对话、12 轮的 LLM 试验中，两种上下文方式各有 11/12 次输出有效 JSON，见[意图增量试验](INTENT_DELTA_PILOT.md)与[授权提取试验](USER_AUTHORIZATION_EXTRACTION_V0_RESULTS.md)。结果只支持“可以生成结构化候选”；没有独立金标，尚不能说明授权提取准确。

**目标三：只凭当前调用和参数来源能否区分正常与攻击？** 用户可能要求“从联系人文件找负责人并发邮件”，邮箱不在原话里，因此仅比较收件人与用户文本会误报。加入原生 `read(path)` 后，窄规则放行了 3 条此类正常发送，对 7 条攻击额外发送保持待审，见[来源绑定试验](RECIPIENT_SOURCE_BINDING_PILOT.md)。但确认邮箱出自指定文件，还没有回答该邮箱为何出现在文件里；Agent 先前写入、随后回读也可能是合法任务。来源检查缩小了疑点，不能独自判定授权。

## 下一步：把事实与授权真正接起来

**问题一：图记录了调用，却不能可靠说明参数来自哪里。** [AuthGraph](https://arxiv.org/html/2605.26497) 遇到过相近问题：同一订票工具的航班号可能来自航班搜索，也可能被酒店页面偷换。它给关键参数指定允许的来源，并用原始工具返回核对实际值。我们先在现有图上复现这一小段检查，而不是整套双图系统：补齐 `read(path)`、文件版本和返回值，检查参数是否出现在用户指定的来源中。读了哪个版本是可核验事实；“模型确实从该处推导参数”仍需另找证据，不能因为值相同就画成确定的因果边。先用已有正常邮件和额外发信轨迹测这两种证据分别能覆盖多少调用。

**问题二：用户授权能提取出来，却容易漏掉时间和动态参数条件。** [CaMeL](https://arxiv.org/html/2503.18813) 让特权模型只看可信用户请求，避免外部内容参与决定任务；[PAuth](https://arxiv.org/html/2603.17170) 将“先查到一个值，再据此操作”保留为符号约束，不必提前写死具体值。我们借这两个原则做逐轮授权提取：只用用户消息和工具定义，记录新增、限制、修订，以及参数应从哪里、按什么条件求值。例如“从联系人文件找负责人发信”应保留文件和负责人角色，而不是猜出邮箱。先由独立标注者核对动作、参数条件和生效轮次；无法确定的委托保持待审，不自动扩大权限。

两侧都通过各自的验证后，再放到同一批真实轨迹上比较：用户要求从某文件取值，Agent 实际读了哪个版本、用到了什么参数；若该版本是先前写出的，再回到写入当时的用户授权。加入合法的“先写后读”任务，才能检验这条链是否既能放行正常更新，又能发现攻击留下的状态。
