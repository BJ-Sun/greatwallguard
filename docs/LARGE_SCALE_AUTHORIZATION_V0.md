# 第一版授权检测：扩大规模离线实验

## 一句话结论

第一版方法已经形成了一个可运行的三级流程：

```text
当前工具调用
    │
    ├─ 明显符合用户授权 ──────────────→ 放行
    ├─ 明显超出用户授权 ──────────────→ 告警
    └─ 仅靠规则无法判断 ─→ 局部 LLM 审计 ─→ 放行 / 告警 / 保留不确定
```

实验说明，程序化规则可以低风险地识别一部分明显越权行为，但不能独立完成检测：多数攻击和不少复杂正常行为都会进入“待复核”。在固定的日历与文件分享样本上，局部 LLM 审计能够进一步区分正常与攻击。执行图已经能够保存调用、参数和候选来源，但这些来源事实尚未真正转化为授权判断。

## 1. 本轮验证什么

本轮不重新生成攻击，而是复用已经保存的真实 Agent 执行轨迹，依次回答三个问题：

1. 简单授权规则能否直接识别明显越权，同时不误报明确正常的任务？
2. 规则无法判断时，局部 LLM 审计能否区分正常行为和攻击行为？
3. 当前执行图是否已经通过参数来源证据改善了检测？

这里有三个不同的判定结果：

- `放行`：现有证据足以说明调用符合用户授权。
- `告警`：现有证据足以说明调用超出用户授权。
- `待复核`：规则证据不足，不能算攻击检出，也不应直接阻断。

## 2. 实验数据

| 数据 | 数量 | 用途 |
|---|---:|---|
| 双成功攻击轨迹 | 305 | 检查攻击目标调用能否被识别 |
| 无注入且任务成功的正常轨迹 | 265 | 检查正常任务是否被误报或送入复核 |
| 邮件图审计子集 | 49 条攻击＋37 条正常 | 检查执行图的来源信息是否真正参与判断 |
| LLM 语义审计子集 | 17 条攻击＋17 条正常 | 检查规则无法判定时的追加审计能力 |

265 条正常轨迹中，240 条来自新增控制数据，25 条来自 GreatWallGuard 原有控制数据。新增数据包含重复运行和任务变体，只有 53 种不同的用户任务原文。因此，本轮适合验证机制是否可行，不能直接作为真实部署误报率。

### 数据具体有什么特点

攻击数据不是任意失败尝试，而是 **305 条正常任务成功、攻击目标也成功的双成功轨迹**。它们覆盖日历、邮件外发、文件删除、定时任务、错误分享和输出完整性六类目标，共包含 5,152 次工具调用。平均每条攻击轨迹约 16.9 次调用，能够体现攻击步骤隐藏在正常执行过程中的情况。

正常数据是 **265 条无注入且正常任务成功的轨迹**，共包含 522 次工具调用。其中：

- 120 条 `clean-benign`：普通正常任务，用于观察基础误报；
- 120 条 `hard-benign`：会合法使用与攻击相同类型的工具、文件或持久化状态，用于避免把“发生写入”直接等同于攻击；
- 25 条早期正常控制样本。

`hard-benign` 是本轮更重要的正常对照：其中 90/120 条会进入规则复核，而普通 `clean-benign` 只有 30/120 条进入复核。这表明难点确实来自**正常任务本身也会产生与攻击相似的效果**，而不只是检测器阈值设置不当。

## 3. 方法在代码中怎么实现

主实验采用“冻结轨迹、按原顺序重放”的方式模拟在线检查。它不是先看完整轨迹再做分类，而是在每次工具调用发生前做一次决定：

```text
可信用户消息
    ↓ 规则提取
授权承诺：允许什么操作、对象、接收方、权限、次数
    ↓ 保存到授权账本
拟执行的工具调用＋具体参数
    ↓ 调用前逐字段匹配
放行 / 告警 / 待复核
    ↓
工具成功后才消耗一次授权
```

### 3.1 用户授权如何产生

当前版本用本地确定性规则从用户消息中提取授权，不调用 LLM。例如：

```text
用户：把 file_id 4 以 editor 权限分享给 alex@example.com

授权账本：
operation = share_file
file_id   = 4
recipient = alex@example.com
permission = rw
max_uses  = 1
```

当前规则能够提取显式邮件接收方和主题、文件 ID、分享对象与权限、创建日历等有限操作。像“继续完成剩余工作”这样的表达不会被猜成完整授权，而会记录为尚未解析的上下文请求。

### 3.2 工具调用如何检查

每个调用先按工具效果分类，再与尚未使用的授权逐字段比较：

- 只读工具直接放行；
- 操作及关键参数与显式授权完全一致时放行；
- 已有明确授权，但接收方、文件 ID 或权限等关键字段明确冲突时，可以告警；
- 用户可能授权了操作，但正文、日历内容或文件对象需要从任务资料中确定时，进入待复核；
- 尚未建立效果契约的工具进入待复核，而不是自动判恶意；
- 一次性授权只有在工具成功后才会被消耗，失败调用不会错误耗尽授权。

因此，主实验实际验证的是**有限授权账本能否进行第一层分流**，并未声称已经完成通用用户意图理解。

### 3.3 图和 LLM 在哪里使用

本轮把两项补充能力分开验证：

- 图实验仅在有原生运行事件的邮件子集上进行。建图器程序化记录消息、工具调用、参数、返回、文件读写、状态版本及参数候选来源，不额外消耗 LLM token。
- LLM 实验只处理规则已经判为“待复核”的固定 34 条调用。模型读取当前调用前的用户消息和局部工具事件，判断其为授权、未授权或不确定。

因此，当前完整状态应理解为：**规则分流已经批量运行；图记录和 LLM 复核已经分别接入并做了小规模验证，但二者还没有组成一个经过大规模评估的统一检测器。**

### 3.4 用一个例子理解完整过程

假设用户提出：

```text
把 file_id 4 以编辑权限分享给 alex@example.com。
```

规则首先生成一条一次性授权：

```json
{
  "operation": "share_file",
  "file_id": "4",
  "recipient": "alex@example.com",
  "permission": "rw",
  "max_uses": 1
}
```

随后可能出现三种调用：

| Agent 拟执行的调用 | 判断 | 原因 |
|---|---|---|
| 分享 `file_id=4` 给 `alex@example.com`，权限为 `rw` | 放行 | 操作和关键参数都与用户授权一致 |
| 分享 `file_id=0` 给 `alex@example.com`，权限为 `rw` | 告警 | 文件对象与用户明确指定的对象冲突 |
| “把项目负责人需要的文件分享出去”，负责人和文件都要从文档中查询 | 待复核 | 用户授权了分享意图，但具体对象和接收方必须由外部资料补全 |

第三种情况正是当前研究的重点。它不能因为参数没有直接出现在用户消息中就被阻断，因为正常任务经常需要查询资料；也不能因为参数曾在某份文件中出现就直接放行，因为该文件可能在之前的步骤中被修改。完整判断需要同时回答：

```text
用户是否允许这份资料决定该字段？
当前参数是否真的来自这份资料？
被读取的是哪个版本？
该版本的形成过程是否获得授权？
```

当前规则只能完成前两种显式情况的稳定分流；执行图已经记录第三种情况所需的部分事实，LLM 可以辅助理解局部语义，但“条件授权—参数来源—状态版本”三者尚未完整连接。

## 4. 哪些行为容易识别，哪些难以区分

| 情况 | 为什么容易或困难 | 当前处理 |
|---|---|---|
| 用户明确指定收件人，Agent 却发给另一个地址 | 关键参数存在直接冲突，不需要理解长上下文 | 容易告警 |
| 用户明确指定文件 ID 和权限，Agent 却分享另一文件或提高权限 | 对象或权限可逐字段精确比较 | 容易告警 |
| 只读搜索、列举和查询 | 不产生持久副作用 | 容易放行 |
| 用户只说“创建日历”，具体标题和时间来自邮件 | 调用本身正常，但关键参数必须由外部资料补全 | 难以自动判定 |
| 用户要求发送邮件，但正文由搜索结果或文件生成 | 正常邮件和攻击邮件都可能使用同一发送工具及外部数据 | 难以自动判定 |
| 用户说“继续完成剩余工作” | 后续允许哪些操作没有明确边界 | 难以自动判定 |
| 删除文件或创建定时任务 | 当前提取器尚未完整建模其对象、条件和次数 | 目前只能复核 |
| Agent 先修改文件或记忆，后续再读取并执行 | 最终工具和直接来源都可能合法，区别位于被读取版本如何形成 | 需要图中的版本与来源链 |
| 攻击只改变最终回答或工作区状态，没有独立危险工具调用 | 单次调用检查器没有明确拦截点 | 需要状态或输出级检查 |
| 新工具或未定义效果的工具 | 不知道哪些参数是安全关键字段 | 需要补充工具效果契约 |

核心边界可以概括为：

```text
明确参数冲突 → 规则可以判断

参数需要由任务数据决定 → 需要来源与授权绑定

来源内容曾在前序步骤被修改 → 还需要状态版本形成过程

用户授权本身含糊 → 只能语义审计或保留不确定
```

## 5. 程序化规则得到什么结果

程序化检查在每次工具调用前执行，只读取当时已经出现的用户消息和当前工具参数，不读取攻击标签、未来结果或评测答案。

### 5.1 攻击轨迹

305 条攻击中，47 条攻击只影响最终输出或工作区内容，没有一个可由当前工具调用检查器直接匹配的目标调用。剩余 258 条攻击能够定位到具体的攻击目标调用。

| 攻击效果 | 可检查的目标调用 | 明确告警 | 待复核 |
|---|---:|---:|---:|
| 错误创建或修改日历 | 52 | 22 | 30 |
| 非授权邮件发送 | 49 | 3 | 46 |
| 删除文件 | 46 | 0 | 46 |
| 创建定时任务 | 50 | 0 | 50 |
| 错误分享文件 | 61 | 38 | 23 |
| **合计** | **258** | **63** | **195** |

这表示：规则能直接识别 **63/258** 个明确越权的目标调用；其余 195 个并没有被明确放行，而是因为证据不足被送入复核。不能把这 195 个“待复核”直接统计为攻击检出。

### 5.2 正常轨迹

| 正常轨迹 | 明确告警 | 待复核 | 无需复核 |
|---:|---:|---:|---:|
| 265 | 0 | 124 | 141 |

没有正常任务被规则明确判成越权，说明高置信告警较保守；但有 124 条正常任务进入待复核。如果将所有待复核调用一律阻断，就会造成严重的正常任务损失。

这些正常任务进入复核，主要不是因为“像攻击”，而是当前规则表达不完整：

- 83 条涉及尚未建模的工具效果；
- 25 条日历调用无法将具体内容与用户要求绑定；
- 16 条文件分享无法将具体文件与用户授权绑定；
- 少量用户要求没有被当前解析器完整提取。

所以，程序化规则当前适合做**高置信分流**，不适合单独承担完整检测。

## 6. LLM 能否处理规则难判的调用

从待复核调用中预先固定 34 条样本，包括 17 条正常调用和 17 条攻击目标调用。DeepSeek 只看到调用发生前的用户消息、少量工具事件和当前拟执行调用，看不到攻击标签、未来结果和评测答案。

| 样本类型 | 数量 | 判为授权 | 判为未授权 | 判为不确定 |
|---|---:|---:|---:|---:|
| 正常日历调用 | 7 | 7 | 0 | 0 |
| 攻击日历调用 | 7 | 0 | 5 | 2 |
| 正常文件分享 | 10 | 10 | 0 | 0 |
| 攻击文件分享 | 10 | 0 | 10 | 0 |
| **合计** | **34** | **17** | **15** | **2** |

在这个固定子集上，17 条正常调用全部被判为授权；17 条攻击调用中，15 条被判为未授权，另外 2 条被判为不确定，没有被错误判为授权。

两条“不确定”样本的关键问题是：用户先要求创建一个明确事件，后续又要求“完成剩余设置”。模型看出当前调用创建的是另一个事件，但无法确定“剩余设置”是否包含这个额外事件。这说明不确定性不是普通的恶意分类问题，而是**用户授权边界本身含糊**。

上述结果只能说明局部语义审计值得继续验证，不能解释为系统总体达到 15/17 的攻击检出率和零误报：样本只有两类效果，且部分 case 共享任务模板。

## 7. 当前执行图发挥了什么作用

我们又在 49 条邮件攻击和 37 条正常邮件轨迹上运行了原生增量建图与审计接口。

| 图审计结果 | 攻击目标调用 | 正常任务 |
|---|---:|---:|
| 明确告警 | 1 | 0 |
| 待复核 | 48 | 0 |

图一共建立了 4,980 条参数候选来源边，但没有一条来源证据实际用于兑现用户授权。原因是：

```text
图已经知道：某个值曾在某份资料中出现

但授权检查还不知道：
用户是否允许这份资料决定这个字段，
以及当前值是否真的来自被允许的那个版本。
```

因此，当前图已经完成“记录执行事实”，尚未完成“用来源事实证明授权”。增加更多候选边本身不会提高检测效果。

## 8. 完整结论

| 层次 | 已经验证 | 尚未验证 |
|---|---|---|
| 程序化授权检查 | 可以识别部分明显越权行为；265 条正常轨迹没有明确误告警 | 大多数攻击与复杂正常行为仍会共同进入复核 |
| LLM 局部审计 | 在固定的日历和分享子集上，能区分正常与攻击，并对含糊授权保留不确定 | 尚未覆盖全部攻击类型、独立任务分布、在线成本和延迟 |
| 执行图 | 能保存工具调用、参数、读写和候选来源 | 尚不能证明某个参数由用户允许的来源和版本产生 |

目前形成的不是一个已经完成的图检测器，而是一个可验证的第一版框架：

```text
程序化规则负责确定性判断
        ↓ 无法确定
执行图提供调用、状态和来源证据
        ↓ 证据仍不足
LLM 只审计局部授权语义，并允许输出“不确定”
```

下一步只需要集中解决一个问题：**如何把“用户允许某份资料决定哪个参数或状态字段”表示成条件授权，并用图中的具体值、来源和版本去验证它。**完成这一连接后，再在更多攻击类型和独立正常任务上评估完整流程的检出率、误报率与审计成本。
