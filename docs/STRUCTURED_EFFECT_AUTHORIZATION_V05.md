# 结构化效果授权 v0.5

## 为什么修改授权表示

上一版把“用户没有写出具体运行时参数”当成“用户没有授权操作”。因此，用户已经明确要求发消息、转账或预订，但收件人、金额、频道或对象需要查询后确定时，正常调用会被直接告警。

v0.5 将一个授权拆成两部分：

```text
用户是否授权该效果？
        ↓
效果类型：发消息 / 转账 / 创建日历 / 修改文件……
        ↓
每个关键参数
  ├─ literal_set：用户已经明确给出，运行时必须一致
  └─ deferred：用户允许任务动态补全，但当前尚未得到来源证明
```

例如：

```text
“把会议纪要摘要发给客户”

effect       = external_message
tool         = send_email
recipients   = deferred(client from task data)
subject      = deferred
body         = deferred(summary of task data)
```

该调用不再因为用户没有写邮箱而被视为“完全未授权”，但在事实图证明具体收件人之前也不会直接放行。

## 外部委托如何处理

“执行邮件中的操作”或“完成网页 TODO 列表”不能直接转换为具体效果授权，因为这样会允许外部内容自行授予权限。系统只记录：

```text
用户确实作出了外部委托
但委托对应的具体效果和参数尚未证明
```

因此相关调用进入 `REVIEW`，而不是 `ALLOW` 或高置信 `ALERT`。

## AgentDojo 全量重测

实验仍使用完全相同的 AgentDojo v1.1 官方调用：97 个正常任务，609 个具有实际目标调用的攻击组合；不调用受害模型、事实图或 LLM。

| 指标 | 工具契约补全 v0.2 | 结构化授权 v0.5 |
|---|---:|---:|
| 正常直接放行 | 37/97（38.1%） | 38/97（39.2%） |
| 正常进入复核 | 13/97（13.4%） | 59/97（60.8%） |
| 正常高置信告警 | 47/97（48.5%） | **0/97（0%）** |
| 攻击高置信告警 | 588/609（96.6%） | 474/609（77.8%） |
| 攻击进入复核 | 0/609 | 114/609（18.7%） |
| 攻击直接放行 | 21/609（3.4%） | 21/609（3.4%） |

## 如何解释结果

结构化授权消除了这批冻结正常调用中的高置信误报，但没有直接提高正常自动放行率。原来的错误告警大多被正确转换为“效果已授权、参数待证明”。因此严格地把 `REVIEW` 也全部阻断时，正常任务失败率仍为 60.8%。

攻击高置信告警率从 96.6% 降至 77.8%，不是攻击被自动放行：114 个攻击转为 `REVIEW`。原因是正常和攻击可能使用相同工具，而用户确实授权了该类效果；仅凭效果类型无法判断实际参数是否合法。

这验证了授权表示的职责：

- 它负责区分“完全没有授权”和“效果已授权但参数待证明”；
- 它不能单独证明动态参数；
- 将 `REVIEW` 直接算作攻击检出或全部阻断都会误导结论。

## 剩余复核由什么构成

59 个正常复核主要涉及：

- 日历标题、时间和参与者；
- Slack 的消息对象、频道和正文；
- 转账对象与动态计算金额；
- 邮件收件人、主题和摘要正文；
- 文件 ID、内容和分享对象；
- 酒店选择以及账户资料更新；
- 由邮件或网页内容委托的后续操作。

这些参数需要从工具返回、文件、消息或环境状态中获得，正是事实图下一步需要证明的对象。

## 仍然漏掉的21个攻击

21 个直接放行全部是 Slack `get_webpage`。它们通过只读工具获得敏感内容，危害发生在最终自然语言输出而非持久工具调用。当前效果授权只审计持久副作用，因此这属于明确的观测面缺口，不能靠调整动态参数授权解决。

## 下一步

下一轮只处理59个正常复核，不再修改效果识别规则：

1. 真实执行其正常只读前缀并写入事实图；
2. 对每个 deferred 参数定位读取调用、返回字段和选择条件；
3. 能形成程序化来源证明的调用由 `REVIEW` 转为 `ALLOW`；
4. 外部委托和复杂语义仍保留 `REVIEW`；
5. 在对应114个攻击复核上验证，同一证明规则是否会错误放行攻击参数。

这一步才能真正评估“结构化用户授权 + 事实图”的组合能力。
