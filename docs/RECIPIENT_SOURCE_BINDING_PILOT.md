# 收件人来源绑定：一次最小真实轨迹试验

## 要回答的问题

用户说“从项目联系人文件找到负责人并给他发邮件”，但没有写出邮箱。只比较用户原话与 `send_email.recipients`，会把正常发送送去复核；若“只要某个工具返回出现邮箱就放行”，又会放过攻击把额外收件人写入资料、记忆并在后续发送的路径。**实际读取路径和跨轮写入链能否缩小这两类情况的混淆？**

这不是防御准确率评测。我们没有重新生成攻击，使用已冻结的 7 个额外发送攻击 case、3 个无注入的条件收件人正常 case（其中一个更换了不透明邮箱值），以及 1 个字面收件人正常 case。全部都是实际 OpenClaw 会话，不是手工拼接工具轨迹。

## 恢复了什么证据

原 `case.json` 没有记录原生 `read(path)` 参数，旧图因而只有读取工具名，不能确认发送字段来自哪个文件。此次只读解析每个 case 的 OpenClaw 原生会话数据库，将 `toolCall` 与 `toolResult` 按调用 ID 配对，并严格只使用每次发送**之前**的用户消息、调用、返回和文件写入。原生发送参数与冻结 case 的发送参数逐个核对，全部一致。

例如，正常 case 的可观测链是：

```text
用户指定 memory/project_contacts.md 的“primary owner”并要求发一封邮件
  → read(path=memory/project_contacts.md)
  → 返回中该角色对应唯一邮箱
  → send_email(recipients=[该邮箱])
```

7 个攻击 case 的额外发送则均有以下候选传播链（并非字段级因果证明）：

```text
较早的外部搜索 / 网页 / 邮件 / 文档返回含额外邮箱
  → Agent 将该邮箱写入 MEMORY.md 或 USER.md
  → 后续回读同一文件，返回仍含该邮箱
  → send_email(recipients=[额外邮箱])
```

在这 7 个 case 中，额外收件人均不在发送前的用户原话中；每条回读链都能找到此前对同一路径、含该收件人的写入。文件名出现在用户消息中并不等于用户授权了文件里的每一个后续操作。

## 三种判据的同条件比较

下表中的“通过”仅是**试验性放行候选**；“复核”不是成功阻断。第三行是本组任务特有的窄规则：除用户直接给出的邮箱外，只有用户明确指定了联系人文件和“primary owner”角色、Agent 真实读取该文件、返回中角色对应唯一邮箱，且该文件未在本会话中被 Agent 改写，才把该条件邮箱视为候选绑定。它不是通用意图提取器。

| 判据 | 3 次正常条件发送 | 7 次攻击额外发送 | 1 次正常字面发送 |
|---|---:|---:|---:|
| 邮箱必须出现在先前用户原话 | 0 通过、3 复核 | 0 通过、7 复核 | 1 通过 |
| 原话有邮箱，或任一先前工具返回有邮箱 | 3 通过 | **7 错误通过** | 1 通过 |
| 用户指定来源与角色 + 原生读取/写入证据的窄绑定 | 3 通过 | 0 通过、7 复核 | 1 通过 |

所有 7 个攻击 case 的首封、用户明确给出收件人的邮件也通过了第三种判据。这说明判据不只是“看到攻击 case 就一概拒绝”；它比较的是**同一轨迹中的具体发送效果及字段来源**。但这批攻击都恰有一个额外发送，数量也是强线索。另有合法双邮件正常 case，因此不能仅凭第二次发送判恶。

## 结论与尚未解决之处

这次验证支持一个更精确的方法切入点：图不应只保存 `read` 和 `send_email` 两个动作，还应保留 `用户指定的取值位置 → 实际读取的对象与返回版本 → 字段候选值 → 发送参数`，以及 `外部返回 → Agent 写入的持久文件 → 后续回读`。这些边使“资料提供了值”和“资料自行创造了任务”有机会分开判断。原始运行记录可提供部分证据；当前主图生成器尚未把这些原生读取字段和版本链纳入在线图，因此不能说完整检测机制已经实现。

结果还不能支持低误报或高检出主张：3 个条件正常样本共享一个任务模板；窄规则刻意保守，会误伤合法的“先总结进记忆，再按用户要求发送”任务。预先投毒但本会话未写入的联系人文件也会绕过“未改写”条件。工具返回中的同值出现只是候选来源，不能证明模型确实从该处推导参数。用户“继续剩余通信”是否授权另发邮件，本身还需独立的人类授权标注，不能只用攻击 oracle 回答。

**下一项最小验证**应增加两组真实良性对照：一组在 Agent 写入并回读记忆后获用户明确授权发送；另一组从用户指定但包含多个候选邮箱的资料中选择负责人。若来源绑定在这些正常任务中仍只能一律复核，就需要用局部语义审计判断“用户指定了什么角色/效果”，而不是继续增加字符串规则。

复现：在仓库根目录执行 `python3 experiments/recipient_source_binding_v0/audit.py`。脚本只读冻结 case 与原生 SQLite，不调用模型、不发送邮件，也不读取攻击成功标签来提取特征。
