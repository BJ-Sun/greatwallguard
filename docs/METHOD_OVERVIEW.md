# GreatWallGuard 方法概览：Progressive Authorization Proof

正常 Agent 的工具路径和参数具有动态性，无法在执行前穷举；但如果把动态规划完全交给 Agent，攻击者又可以借外部网页、邮件、文件或记忆影响规划，新增工具、替换参数并扩大最终效果。例如，用户只要求购买一台相机，正常 Agent 可能动态搜索商品、查看详情、加入购物车并结算；恶意网页也可能诱导它额外发送用户信息。固定工具序列会误拦前者，完全开放工具选择则会放过后者。因此，我们要解决的不是“Agent 是否偏离某条预生成计划”，而是“动态产生的行为是否仍能由用户授权解释”。

长程攻击可以把目标拆成多个局部合理的步骤，但要跨步累积并最终造成可观察危害，至少一个步骤必须留下可被后续利用的状态，或直接改变外部环境。我们将这类安全相关的真实后果统一定义为 **Effect**，包括发送消息、转账或购买、删除或发布资源、修改文件与配置、写入记忆、改变权限和凭据，以及创建可在后续触发的任务；其中，最终实现用户目标或攻击目标的后果称为终端 Effect。Effect 的安全性不仅取决于调用了什么工具，还取决于关键参数如何形成。我们将关键参数从用户字面值或运行时数据出发、经过筛选和计算后流入 Effect 的关系定义为 **Binding**。由此，防御问题可以转化为：在 Effect 即将发生或持久状态即将被后续使用时，识别用户授权行为与被误导 Agent 行为之间的差异。该差异由简到难依次表现为：新增终端 Effect；工具路径不同但可能是正常动态执行；同一工具下固定参数错误；动态 Binding 的来源或计算过程错误；以及工具、来源和数据流均相似、只有任务语义不同。仍以购物任务为例，额外发送邮件属于新增 Effect，`add_to_cart` 可能只是正常中间工具，购买数量错误属于固定参数冲突，购买的商品不是搜索结果中评分最高者属于动态 Binding 冲突，而“最适合出差的相机”是否对应某个候选商品则属于语义未决关系。

我们的目标是在不固定唯一执行路径的情况下，为每个真实 Effect 建立一条从可信用户请求到实际工具调用的授权证明。关键观察是：无论执行过程如何动态变化，外部内容都不能自行新增终端 Effect、扩大被操作的对象和数据范围，或绕过用户规定的条件与预算。基于这一边界，我们提出 **Progressive Authorization Proof**：差异越明显，越优先使用便宜、确定且可复核的程序证明；只有当 Effect、工具能力、参数来源和计算过程均无法形成明确结论时，才将剩余的一条局部语义关系交给受约束的语义审计模块。审计模型接收的不是完整轨迹，而是程序确定的原子问题及其最小证据，并且只能在既有 Effect、字段和候选值范围内给出结论。系统因此不是为不同攻击分别增加检测规则，也不是让另一个模型重新判断整个任务，而是按照授权关系的可判定程度，从结构、关系逐步深入到语义。

Progressive Authorization Proof 由三个前后衔接的子方法组成。**Authorization Compilation** 将可信用户请求和工具契约编译为路径无关的 Authorization DAG，使终端 Effect、关键参数的合法形成关系、委托边界、适用条件和消费预算成为可执行的授权规范。**Deterministic Runtime Proof** 将真实工具调用和返回绑定到该 DAG，按照终端 Effect、动态读取与中间能力、固定参数和动态 Binding 的顺序验证候选调用，并将结果区分为已证明授权、明确冲突和尚未闭合。**Semantic Proof Completion** 将尚未闭合的具体关系转换为原子 Proof Obligation，从授权 DAG 与运行时证据中切取最小证据，由隔离的审计模型给出 `SUPPORTED / CONTRADICTED / NEED_EVIDENCE` 三态语义证明，再由程序验证冲突证书、执行有界补证或路由到用户确认。三个子方法共同完成授权规范构造、确定性运行时验证和受约束语义判定，而不是三个彼此独立的检测器。

完整流程可以用购物案例串联。用户要求“从指定目录中购买价格低于 500 元且评分最高的相机”，阶段一生成 `search_products → select(price<500) → argmax(rating) → project(product_id) → checkout` 的授权关系，但不固定商品 ID 和中间工具顺序。运行时若 Agent 调用 `send_email`，阶段二在 Effect 层直接拒绝；若调用 `add_to_cart(P17)`，系统根据工具能力契约和对象连接判断它是否为 `checkout(P17)` 的正常中间步骤；若调用 `checkout(P99)`，系统用真实搜索结果执行 DAG，比较授权计算结果与实际参数；若用户改为“购买最适合出差的相机”，有限算子无法判断 P17 是否满足该语义，阶段三只审计“P17 是否符合最适合出差”这一原子关系。最终，明显偏离被低成本阻断，正常动态路径由关系证明容忍，真正难以程序化的语义才进入受约束审计。

```text
可信用户请求 + 工具／效果契约
              │
              ▼
① Authorization Compilation
   自然语言 → Authorization DAG
   构造可执行授权规范
              │
              ▼
② Deterministic Runtime Proof
   Effect → 动态工具 → 固定参数 → 动态 Binding
   完成结构与关系证明
              │
        ┌─────┼─────┐
      ALLOW  REVIEW  ALERT
              │
              ▼
③ Semantic Proof Completion
   原子问题 → 最小证据 → 三态语义证明
              │
              ▼
       ALLOW / DENY / CONFIRM
```
