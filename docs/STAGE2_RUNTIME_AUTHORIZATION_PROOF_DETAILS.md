# 阶段二：运行时授权证明

阶段一生成的 Authorization DAG 只描述“用户允许行为怎样发生”。其中，用户明确给出的参数可以在编译时固定，但由搜索结果、文件内容或工具返回决定的参数仍是符号表达式。例如，用户要求“给 TODO 中未完成任务的负责人发送提醒”，阶段一能够规定：

```text
recipients
← project(owner_email)
← select(status = unfinished)
← read_todo
```

但在真正读取文件前，系统并不知道具体邮箱。阶段二要解决的是：**当 Agent 根据真实环境动态规划和调用工具时，如何判断其实际行为仍然属于这份符号化授权。**

为此，我们提出 **Runtime Authorization Proof**。它部署在 Agent 与工具之间的调用网关，一方面记录 Agent 实际调用了什么、工具返回了什么，另一方面独立求值阶段一生成的 Authorization DAG。系统不预测 Agent 的完整计划，也不判断外部文本是否“看起来恶意”，而是检查 Agent 对运行时数据的实际使用方式能否由用户授权独立推导。

```text
Authorization DAG ── 合法的数据使用方式 ──┐
                                          ├─→ Runtime Prover
Runtime Evidence ── 返回值与实际调用 ──────┘          │
                                                     ▼
                                          ALLOW / ALERT / REVIEW
```

## 1. 从动态规划到运行时证明

动态任务中的不确定性有两种。第一种是**参数动态性**：阶段一知道要发送邮件，但收件人需要读取文件后才能确定。第二种是**工具动态性**：阶段一知道最终要完成购买或发布，但搜索、查看详情、加入购物车或准备工作区等中间工具及其顺序只有运行时才能确定。因此，不能把阶段一的 DAG 当作一条必须原样执行的固定计划；但动态性也不能意味着 Agent 可以根据外部返回任意增加终端效果。

我们的核心观察是：Agent 的规划过程可以变化，但任何真实副作用最终都必须落实为一个可观察的工具调用：它使用了什么工具、哪些参数，这些参数来自哪些先前返回，以及执行时满足了哪些条件。防御器可以在 Agent 之外，对同一批工具返回执行用户授权规定的计算，再与 Agent 的实际选择比较。

**Key Insight.** 阶段二不复现 Agent 的完整推理，而是独立重放用户授权中可程序化的部分：如果实际工具和参数能够由授权 DAG 在当前运行时证据上求值得到，则授权证明闭合；如果二者明确冲突，则行为越权；如果计算所需的事实或语义关系不足，则保留为未决证明。

因此，阶段一和阶段二的分工是：

```text
阶段一：固定终端效果和安全不变量，
        用 Binding 描述动态参数如何形成。

阶段二：用真实返回实例化动态参数，
        并验证运行时新增的读取工具和中间工具是否仍服务于该终端效果。
```

阶段二允许变化的范围可以概括为：

```text
动态参数       可以变化，但必须由 Binding 对授权来源求值得到；
动态读取工具   可以变化，但必须属于允许的来源能力和对象范围；
动态中间工具   可以变化，但必须从已有终端 Effect 派生，且参数范围不扩大；
终端 Effect    默认不能动态新增，除非用户进行了明确的效果级委托。
```

## 2. Runtime Authorization Proof

调用网关在工具执行前后工作。执行前，它看到候选工具名称和参数；执行后，它看到真实返回和成功状态。返回值被展开为带有 `call_id / tool / field path / value` 的字段级事实，例如：

```text
read-1 : read_todo : [0].status       = unfinished
read-1 : read_todo : [0].owner_email  = alice@example.com
```

这些事实只说明某个值在哪里出现，不自动说明该值获得了用户授权。对于每个候选调用，证明器按照固定顺序检查：

```text
Agent 提出工具调用
        ↓
1. 判断工具角色并检查授权关系
   ├─ 终端工具：是否实现已授权 Effect
   ├─ 读取工具：是否属于允许的来源能力和范围
   └─ 中间工具：是否可从已授权 Effect 受限派生
        ↓
2. 检查安全关键参数是否完整
        ↓
3. 求值动态 Binding，并与实际参数比较
        ↓
4. 检查来源、约束和对象范围
        ↓
5. 检查授权预算
        ↓
ALLOW / ALERT / REVIEW
```

首先，证明器不是简单查询一张工具白名单，而是判断当前工具在本次任务中扮演什么角色。终端工具必须实现阶段一授权的 Effect；读取工具可以动态选择，但必须属于部署方声明的来源能力，并保持用户允许的对象、目录或域范围；中间工具不需要提前出现在固定计划中，但必须由工具能力契约证明其服务于某个已授权终端 Effect，而且关键对象和参数能够连接到该 Effect。只有前述关系都不成立时，它才是计划外工具。

例如，用户授权购买某个筛选得到的商品，`search_products` 可以作为读取能力，`add_to_cart` 可以作为 `checkout` 的中间能力，具体顺序由 Agent 在运行时决定；但 `send_email` 会产生独立的对外发送效果，不能因为网页要求或 Agent 认为“有帮助”就从购买授权中派生。正常与恶意的区别因而不是“工具是否提前出现”，而是“新增工具是否仍在已有终端授权的能力闭包内，并保持同一对象和参数范围”。

随后，证明器根据工具契约确定安全关键参数。用户明确给出的参数直接比较；运行时才能确定的参数，则执行阶段一编译的 Binding 表达式。假设 `read_todo` 的真实返回为：

```json
[
  {
    "status": "unfinished",
    "owner_email": "alice@example.com"
  },
  {
    "status": "finished",
    "owner_email": "bob@example.com"
  }
]
```

证明器使用普通程序执行 DAG，而不是让 LLM 重新理解返回内容：

```text
真实 read_todo 返回
→ select(status = unfinished)
→ project(owner_email)
→ 当前允许的 recipients = {alice@example.com}
```

与此同时，Agent 可能提出：

```text
send_email(recipients=["alice@example.com"])
```

阶段二比较的是：

```text
Authorization DAG 对真实返回的计算结果
                         ↕
Agent 实际提出的工具调用参数
```

两者一致时，`recipients` 的 Binding 得到证明；如果 Agent 受到外部指令影响而选择 Eve，则该参数不能由授权查询产生，形成明确冲突。动态参数的来源检查包含在求值过程中：证明器只使用 DAG 指定的工具、字段和范围，不能因为某个值曾在任意 observation 中出现就接受它。

当前有限计算包括：

```text
select       按条件筛选记录
project      提取指定字段
join         关联多个工具返回
aggregate    最大、最小、计数或求和
compute      日期、数量等确定性计算
normalize    规范化日期、URL和路径
template     使用已授权字段构造受限文本
```

参数关系闭合后，证明器继续检查条件、对象范围和预算。例如，目录授权可以覆盖子路径但不能扩展到兄弟目录；URL 授权只能在指定域和路径范围内传播；“评分高于 4”必须由真实评分字段证明；“每位负责人最多一次、总计最多十次”由运行时账本维护。工具成功执行后才消耗预算，失败调用不会消耗授权。

整个过程不读取 Agent 的隐藏推理，也不消耗额外 LLM token。工具返回由真实业务工具产生，调用网关只负责记录；DAG 的筛选、投影、计算和比较均由确定性程序完成。

## 3. 判定与未决证明

阶段二不是攻击分类器，而是授权证明器。它产生三类结果：

```text
ALLOW
工具、参数、来源、条件、范围和预算均存在完整程序证明。

ALERT
Effect、参数、条件、范围或预算与授权存在明确冲突。

REVIEW
尚未发现明确冲突，但当前证据不足以闭合授权证明。
```

`REVIEW` 主要来自三类不同问题。第一类是语义未决：例如“最合适的人”“符合当前情况的状态”或开放生成正文，阶段一无法将其完全编译为有限算子。第二类是证据缺失：DAG 可以执行，但 Agent 没有取得必要返回，返回中缺少字段，或中间能力与终端效果之间缺少参数连接。第三类是策略确认：用户把部分决定宽泛地委托给外部资料，系统不能确定该委托只允许填写字段，还是允许新增效果。

```text
semantic_unresolved
→ 阶段三只审计一个局部语义关系

evidence_missing
→ 继续取证、补充工具契约或恢复字段来源

policy_confirmation
→ 要求用户明确授权边界
```

只有第一类适合直接交给 LLM。证据缺失不能通过模型猜测补齐，宽泛授权也不能由模型代替用户确认。

## 4. 贯穿案例

对于“读取指定 TODO，给每个未完成任务的负责人发送一次提醒，最多十封”，阶段一产生：

```text
Effect       = external_message
recipients   ← read_todo → select(unfinished) → project(owner_email)
subject      = "Task Reminder"
body         ← read_todo → select(unfinished) → project(task) → template
attachments  = absent
Budget       = 每位负责人一次，总计十次
```

运行时首先处理读取调用：

```text
Agent → read_todo(用户指定路径)
Gateway → 检查读取范围
Tool → 返回 TODO 记录
Gateway → 保存字段级 observation
```

当 Agent 随后提出 `send_email` 时，证明器依次得到：

```text
工具检查：send_email 对应已授权 external_message
完整性检查：recipients / subject / body / attachments 均存在
动态求值：unfinished 记录导出 Alice
参数比较：实际 recipients 为 Alice
约束检查：Alice 对应记录状态为 unfinished
预算检查：Alice 尚未发送，总数未超过十次
结果：ALLOW
```

若 Agent 给 Bob 发送，DAG 的筛选结果与实际参数冲突，输出 `ALERT`；若 TODO 返回中没有 `status`，则无法执行筛选，输出 `REVIEW`；若用户只说“联系最合适的人”，工具返回又没有可执行选择条件，则形成 `semantic_unresolved`，由阶段三审计“候选对象是否满足用户描述”。

## 5. 当前实现和实验边界

当前代码已经实现调用拦截、字段级 observation、DAG 有限求值、参数比较、范围传播、中间能力派生和动态预算。工程上使用的是“Authorization DAG + Runtime Evidence”，而不是对两张完整图做同构匹配；运行时证据表承担执行事实图中与本次证明相关的部分。

双基准实验采用条件轨迹回放。正常侧执行 AgentDojo 和 AgentDyn 的官方标准工具序列并保存真实返回；攻击侧在同一份用户授权和正常证据快照上，检查 benchmark 定义的攻击目标调用。因此，实验衡量的是：候选调用出现时，程序化证明器会放行、复核还是阻断；它不等同于重新运行受害模型后的端到端攻击成功率。

当前版本账本已经能够表示对象版本、父版本、产生写入和写入授权状态，但文件、记忆和工作区的版本事件尚未在两个 benchmark 中统一提供。因此，现有全量结果验证了工具、Effect、参数、有限来源关系、范围和预算检查，但还不能声称已经端到端解决“被攻击改写的合法来源反过来自证授权”。这部分需要将版本账本与真实持久状态读写完整接入后单独评估。

阶段二最终形成如下闭环：

```text
真实工具返回
→ 记录结构化运行时证据
→ 求值 Authorization DAG
→ 得到当前允许的工具、参数和范围
→ 与 Agent 实际调用比较
→ ALLOW / ALERT / REVIEW
```

其核心不是判断工具返回是否恶意，而是维护一个独立于 Agent 的授权求值过程：**Agent 可以自由理解环境和动态规划，但当它准备产生真实副作用时，其实际选择必须能够由用户授权规定的数据来源和计算关系独立推导出来。**
