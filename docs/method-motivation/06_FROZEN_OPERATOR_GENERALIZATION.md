# 第六步：从任务适配转向冻结算子泛化

## 问题

当前关系证明把正常自动放行从38/97提高到61/97，但这些任务在开发过程中已被查看。这个结果证明算子可以解释轨迹，却不能证明面对未见任务时仍然有效。如果每个任务都要先看正确轨迹再增加规则，方法就退化为 benchmark fitting。

## 方法边界

后续不再以“消灭剩余复核”为目标。程序化层被冻结为一套小型关系语言：

```text
取值：从用户、指定实体或授权来源获得字段
变换：筛选、连接、排序、聚合与确定计算
约束：检查唯一性、条件谓词和最终效果边界
```

用户请求与工具 Schema 只负责把任务编译成这些关系的实例；运行时 observation 负责提供事实。算子集合不能因测试任务而改变。

## 当前证据到底有多强

对v2.7证明日志进行复用审计后，共观察到15种证明规则：

- 1种跨越多个业务域复用；
- 8种在同一业务域的多个任务中复用；
- 6种目前只在一个任务中出现。

因此，现有结果适合证明工程可行性，但不足以声明跨任务泛化。尤其是条件守卫、自然日期、排名模板和两种分组聚合，目前仍只有单任务支持；它们即使概念上通用，也必须由未见任务验证。

攻击回归只能说明这些算子在当前629组对照上没有新增攻击证明，不能替代未见任务测试。

## 决定性实验

从当前版本开始冻结：

1. 算子语义与安全关键字段契约固定；
2. 不根据测试轨迹新增正则、字段名或工具特例；
3. 在未参与开发的新任务或其他 benchmark 上，仅允许自动编译和实例化现有关系；
4. 分别报告自动证明、语义复核、明确拒绝和无法编译，而不是把复核算成检测成功；
5. 若需要新增算子，只能进入下一版本，并重新选择新的未见测试集。

冻结文件及其 SHA-256 记录在 `experiments/frozen_operator_v27_manifest.json`。测试阶段只允许编写事件格式适配器，以及在查看结果前声明工具 Schema 到效果契约的映射；二者都不能改变关系算子的判定语义。

评价重点不是单独追求放行率，而是同时测量正常自动证明率、正常复核率、攻击告警率、攻击被错误证明率，以及每种算子的未见任务覆盖情况。

## 当前结论

当前系统已经形成了可冻结的算法骨架，但尚未完成严格泛化验证。下一步最有价值的工作不是继续针对剩余36个任务补规则，而是把v2.7作为冻结版本接入新的任务分布，检验这三类关系是否能够自动实例化。
