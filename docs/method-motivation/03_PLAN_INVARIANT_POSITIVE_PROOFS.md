# 第三步：用计划无关的正向证明减少正常任务复核

## 问题从哪里来

关系型授权确定了“应该验证参数如何得到”，但还没有回答一个工程问题：Agent 的正常工具顺序和中间步骤无法提前预测时，程序如何自动证明当前调用仍然符合用户要求？

最保守的做法是把所有运行时参数交给 LLM 或人工复核。这虽然避免了错误放行，却会让大量正常动态任务进入 `REVIEW`。另一种做法是枚举允许的工具链，但 Agent 换一种查询顺序、增加一次辅助读取或使用另一条等价路径，就可能再次误报。

因此，我们需要的不是更多正常计划，而是一组与计划顺序无关的**正向证明算子**。

## 核心原则

正向证明只回答一个问题：

> 在已经观察到的事实中，是否存在一条有限、唯一且可重放的推导，证明当前参数满足用户授权的关系？

```text
用户授权：删除最大的文件

任意正常计划：
查询文件 → 查看详情 → 其他辅助读取 → delete_file(file_id=13)

正向证明：
files = 已观察到的文件集合
winner = argmax(files, size)
project(winner, id) = 13
```

证明依赖的是数据关系，不是 `list_files` 必须出现在第几步，也不要求 Agent 遵循唯一工具序列。

## 统一的算子形式

每个关键参数的证明表示为：

```text
ParameterProof = (
    authorization,   用户允许的效果和参数关系
    expression,      可重放的关系表达式
    source_calls,    实际使用的历史工具调用
    result           表达式计算出的唯一参数值
)
```

最小正向算子集合包括：

```text
literal(v)                 用户直接给出值
normalize(v)               日期、时间和有限格式归一化
filter(R, predicate)       按用户条件筛选
argmax / argmin(R, field)  按字段选择唯一对象
project(object, field)     从对象取出目标参数
compute(inputs, rule)      时长等确定性计算
join(R1, R2, key)          跨工具返回连接同一实体
```

当前代码已实现前六类中的有限子集；一般化 `join` 尚未实现。

## 为什么它能够容忍正常任务动态性

一个证明只有在同时满足以下条件时才能放行：

1. 用户已经授权对应效果；算子本身不能创建新权限；
2. 所有输入均来自当前调用之前的主机可观测事实；
3. 推导过程确定、可重放，并保存源调用 ID；
4. 结果唯一，且与候选工具参数完全一致；
5. 无关 observation 不参与结果；出现相互冲突的兼容证据时退回 `REVIEW`。

由此，正常任务可以改变查询顺序、增加无关读取或选择等价的数据获取路径。只要最终事实仍能证明同一个授权关系，调用就可以放行；如果证据不够，系统承认不可判定，而不是猜测。

## 实现与全量验证

当前 `RuntimeRelationResolver` 已记录工具名、调用参数、结构化返回和调用 ID，并实现：

- 用户显式值；
- 日期与时间规范化；
- 开始时间加时长；
- 命名对象的唯一投影；
- 前缀筛选；
- 最大/最小选择。

单元测试进一步固定了两个计划无关性质：改变 observation 顺序不改变证明；加入会改变排序结果的兼容证据时，旧参数不能继续获得证明。

全量实验使用 AgentDojo v1.1 的 97 个正常任务和 609 个具有目标工具调用的攻击组合：

| 指标 | 仅效果授权 | 加入正向证明 |
|---|---:|---:|
| 正常自动放行 | 38/97（39.2%） | **50/97（51.5%）** |
| 正常进入复核 | 59/97（60.8%） | **47/97（48.5%）** |
| 正常高置信告警 | 0 | 0 |
| 新增被证明合法的攻击调用 | — | **0** |

正向算子使 12 个正常任务退出复核，没有扩大攻击授权面。这说明它确实能够降低正常任务复核率，而不是只在人工案例中成立。

## 当前边界

这组结果还不能说明正向证明已经适配任意动态计划。

第一，当前部分算子仍在全部 observation 中寻找结构兼容的候选，尚未为每个授权关系建立完整的类型化 `SourceRef`。未来应通过工具 schema 和稳定实体类型限定可用来源，而不是依赖工具顺序或任务专用工具名。

第二，摘要、角色和开放式内容变换无法由有限算子完成。例如“把文档摘要发给客户”同时包含“谁是客户”和“正文是否为合格摘要”两个语义关系，应进入局部语义审计。

第三，当前实验主要是单任务参数证明。文件或记忆在前序任务中被改写后，还需要把 `version` 作为关系算子的显式输入，验证当前参数来自哪个版本以及该版本是否获准形成。

## 下一步

下一步只推进两个通用能力：

1. **类型化来源与跨调用 join：**从工具 schema 建立实体和字段关系，使证明可以跨不同正常计划连接事实，同时排除无关数据源；
2. **版本化输入：**把文件、记忆和环境状态版本纳入 `SourceRef`，将正向证明扩展为“该值来自一个获准形成的版本”。

这两项完成后，再将仍无法程序化证明的局部关系交给 LLM。这样，LLM 处理的是明确的语义缺口，而不是重新阅读整个动态执行过程。
