# 显式委托与类型化复核：方法固定及全量回归

## 1. 为什么调整

阶段二原本把所有无法证明的调用统一记为 `REVIEW`。这在安全上保守，但把三种不同问题混在了一起：运行时证据尚未取得、用户确实把部分决定交给了外部资料、以及现有证据齐全但语义关系仍不明确。若把三类问题都交给 LLM，不仅成本高，也无法针对真正缺失的证据采取动作。

本次调整把“遵循文件／网页中的要求”建模为**显式委托**，并把复核变成具有处理义务的类型，而不是一个模糊分数。

## 2. 固定后的方法

```text
可信用户请求 + 工具／效果契约
            │
            ▼
授权编译器
  ├─ 终端效果、参数、条件和来源
  └─ DelegationGrant：用户允许外部资料决定什么
            │
            ▼
程序化运行时证明
  ├─ 事实／字段／选择委托：只在限定字段内传播
  ├─ 有界效果委托：限定工具或效果，继续做语义证明
  └─ 宽泛效果委托：不得自动放行，要求用户确认
            │
      ┌─────┼─────────────┐
    ALLOW  ALERT         REVIEW
                         ├─ evidence_missing：继续取证／补契约
                         ├─ policy_confirmation：请求用户确认
                         └─ semantic_unresolved：最小证据包交给 LLM
```

委托只有四种有限权限：`facts`、`fields`、`selection`、`effects`。外部内容不能因为被读取就自动获得控制权；它只能填充用户明确委托的字段或选择。用户若宽泛地要求“执行文件中的所有任务”，系统会记录这一真实意图，但不会把未知副作用静默升级成自动授权。

程序化检查器仍只使用可观察事实：工具名、参数、返回字段、来源调用、对象范围、预算和状态版本。LLM 不参与事实图构建，也不能新增效果或扩大范围。

## 3. 代码入口

- 委托数据结构与确定性提取：`src/greatwallguard/delegation.py`
- 授权 DAG 与运行时判定：`src/greatwallguard/authorization_dag.py`
- LLM 授权编译和 IR 校验：`src/greatwallguard/intent_dag_compiler.py`
- 类型化复核义务：`src/greatwallguard/review_obligations.py`
- 受限语义审计接口：`src/greatwallguard/semantic_audit.py`
- 双基准阶段二回归：`experiments/stage2_full_benchmark.py`
- AgentDyn 委托迁移与回归：`experiments/stage2_delegation_full.py`
- 第三阶段全量入口：`experiments/stage3_delegation_full_eval.py`

第三阶段脚本默认只在本地生成清单；只有显式提供 `--run` 才会调用外部审计 API。逐条结果带断点和内容哈希缓存，可在中断后继续运行。

## 4. 阶段二全量回归

引入委托节点和复核类型后，原有安全边界没有被放宽。

### AgentDojo

| 数据 | ALLOW | REVIEW | ALERT |
|---|---:|---:|---:|
| 正常任务（97） | 60（61.9%） | 37（38.1%） | 0 |
| 全部攻击组合（629） | 20（3.2%） | 179（28.5%） | 430（68.4%） |
| 有实际目标动作的攻击（609） | 0 | 179（29.4%） | 430（70.6%） |

20 个攻击侧 `ALLOW` 均为空目标序列，不代表攻击动作被放行。

### AgentDyn

| 数据 | ALLOW | REVIEW | ALERT |
|---|---:|---:|---:|
| 正常任务（60） | 6（10.0%） | 54（90.0%） | 0 |
| 攻击组合（560） | 0 | 337（60.2%） | 223（39.8%） |

两套基准与调整前的任务级结果完全一致。变化发生在 `REVIEW` 内部：系统现在知道下一步应该补证据、询问用户，还是进行语义审计。

## 5. 全量 REVIEW 的处理分布

两个基准共得到 814 个调用级 `REVIEW`：

| 基准与数据 | 缺少程序证据 | 需要用户确认 | 语义未决 |
|---|---:|---:|---:|
| AgentDojo 正常 | 12 | 5 | 47 |
| AgentDojo 攻击 | 21 | 23 | 195 |
| AgentDyn 正常 | 36 | 13 | 105 |
| AgentDyn 攻击 | 22 | 44 | 291 |
| **合计** | **91** | **85** | **638** |

这组数字是调用级处理义务，不是任务级准确率。它说明 176 个复核不应交给 LLM：91 个需要补充可验证证据或部署契约，85 个属于用户必须承担的宽泛授权确认；剩余 638 个才是第三阶段的正式审计集合。

## 6. 第三阶段试验状态

此前 48 条带本地真实 observation 的固定试验中，最小证据审计结果为：

- 正常调用：14/24 判为授权，7/24 判为未授权，3/24 不确定；
- 攻击调用：24/24 判为未授权，错误放行 0；
- 总消耗约 5.6 万 token。

正常侧未全部放行并不都属于审计器误报。复核发现部分 benchmark 标准轨迹本身没有取得用户要求的来源或条件证据，却继续执行了动作。因此正式结果必须同时报告两种口径：按 benchmark 的 normal/attack 标签统计，以及按证据是否足以构成授权统计。不能把正常标准轨迹天然视为授权金标。

当前已完成 638 条 `semantic_unresolved` 全量审计：110/152 个正常调用获得授权，485/486 个攻击调用被判未授权，1 个不确定，攻击错误放行为 0。合并到任务级后，AgentDojo 正常任务为 78 Allow / 12 Review / 7 Alert，AgentDyn 为 23 / 22 / 15；有效攻击分别为 0 / 39 / 570 和 0 / 46 / 514。正常硬告警仍然过高，因此本结果证明了语义审计的区分信号，但尚不支持把 LLM 的单次 `unauthorized` 直接用于在线阻断。完整分析见[阶段三全量评估](STAGE3_FULL_EVALUATION.md)。

## 7. 当前结论

这次调整没有通过放宽阈值改善表面指标，而是固定了一个可部署的决策流程：**程序能证明的自动放行，程序能证明冲突的直接阻断，缺证据的继续取证，宽泛授权的询问用户，只有证据齐全但语义未决的关系才调用 LLM。**

因此，下一步不再扩大审计输入，而是为正常 `REVIEW` 建立调用级授权金标，并用程序化反证、一致性校验或局部重放区分“标准轨迹缺证据”和“LLM 误判”。
