# 程序化规则完善实验

## 实验目标

第一版中，部分调用进入复核只是因为工具效果没有定义或授权提取器不认识相应操作。本轮补齐当前数据中出现的工具契约，并重新运行全部570条轨迹，以区分“工程实现不足”和“规则原理上无法判断”。

## 本轮实现

- 为网络观察、网络扫描、网页访问、日历修改、文件创建与追加、文件删除、定时任务、调度触发和命令执行建立有限效果契约；
- 从可信用户消息中提取明确的目标主机、端口、事件修改、文件对象和调度授权；
- 明确参数一致时放行，明确对象冲突时告警；
- 参数依赖外部资料、对象需要查询或用户表达含糊时保留复核；
- 未使用额外LLM，14项单元测试通过，570条轨迹重放无运行错误。

## 结果

| 指标 | 完善前 | 完善后 |
|---|---:|---:|
| 可检查攻击目标的高置信检出 | 63/258（24.4%） | 63/258（24.4%） |
| 全部攻击的高置信检出 | 63/305（20.7%） | 63/305（20.7%） |
| 攻击目标待复核 | 195/258（75.6%） | 195/258（75.6%） |
| 正常任务明确告警 | 0/265（0%） | 0/265（0%） |
| 正常任务待复核 | 124/265（46.8%） | 79/265（29.8%） |
| 若将所有风险直接阻断，正常任务成功率 | 141/265（53.2%） | 186/265（70.2%） |

程序化完善使45条正常任务不再需要复核，同时保持明确假阳性为0；但没有新增任何冻结攻击目标的高置信检出。

## 为什么没有提升攻击检出

原先标记为“操作未提取”的删除和定时任务，在补齐工具定义后暴露出真正问题：用户使用的是“处理队列项”“完成记录中的处置”“为下一周期做好准备”等业务表达。这些话可能隐含删除或未来任务，也可能只是要求整理状态。仅靠程序化规则无法在不误伤正常任务的前提下，将其直接解释为授权或越权。

因此，原先将58条攻击视为纯工程缺口并推算46.9%的检出上界并不成立。本轮实测后的可靠结论是：

```text
程序化规则的高置信检出边界：24.4%（可检查攻击口径）
程序化规则可将正常任务复核率：46.8% → 29.8%
剩余攻击目标复核：全部具有上下文授权或参数绑定原因
```

## 剩余正常复核的含义

79条正常任务仍需复核，主要包括：

- 日历事件名称需要通过查询结果绑定到事件ID；
- 用户授权了文件分享，但具体文件需要从任务资料中确定；
- 用户允许验证HTTPS服务，但Agent扩大端口集合或省略端口；
- 用户要求“报告”或“记录”，但没有说明应回复消息、创建文件还是追加日志。

这些问题已经不是“工具不认识”，而是需要结合来源、参数角色和任务语义判断。

## 结论

程序化层已经达到当前数据上的合理边界：它能够低成本处理明确授权和显式参数冲突，并将正常任务复核率降至29.8%；但不能提高对隐蔽长程攻击目标的高置信检出。下一步不应继续堆叠正则，而应让执行图验证参数来源和状态版本，再由局部语义审计处理授权含糊的少量调用。
