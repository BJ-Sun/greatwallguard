# GreatWallGuard 方法总览与协作入口

本文是当前方案的统一入口，供后续开发和实验协作者直接使用。阅读后应能回答四个问题：我们解决什么问题、当前方法是什么、哪些已经实现、下一步如何验证。

## 1. 研究问题

长程 Agent 会连续接收用户指令，并根据邮件、网页、文件和记忆决定后续操作。攻击步骤可以单独看起来合理，却通过写入文件、修改记忆、创建任务或改变关键参数，在后续步骤中形成危害。

因此，单纯判断某段输入是否恶意，或者检查最终调用是否使用了允许的工具，并不足以回答真正的授权问题：

> 截至当前时刻，用户究竟授权了什么操作、对象和参数；当前调用是否符合这份授权；调用所依据的外部值或状态版本是否有权决定相应参数？

第一版先解决其中可以在线落地的部分：**从可信用户消息形成结构化授权，并在每次工具调用前进行低成本检查。**

## 2. 当前方法

```text
可信用户消息 + 可用工具环境
            ↓
    结构化授权提取
  操作 / 对象 / 参数 / 次数 / 条件
            ↓
       跨轮授权账本
            ↓
Agent 提议的工具调用与参数
            ↓
        程序化检查
     ┌──────┼────────┐
   ALLOW   ALERT    REVIEW
   明确一致  明确越界  证据不足
                        ↓
              局部来源/版本/LLM审计
```

程序化检查是第一层，不负责猜测所有业务语义：

- 用户明确允许某个操作，且关键参数一致，返回 `allow`；
- 没有对应授权，或对象、接收方等显式关键参数冲突，返回 `alert`；
- 参数需要从文件、邮件或记忆中补全，或者用户表达只能确定大致任务，返回 `review`。

`review` 不是攻击标签，也不应默认阻断。它表示程序事实不足，需要下一层检查参数来源、状态版本或局部任务语义。

## 3. 已固定的算法基础

当前固定为 Programmatic Core v0.1：

1. 只有经过身份验证的用户消息能够增加授权；外部返回、文件和记忆不能自行扩张权限。
2. 授权按工具效果、关键参数和有限使用次数表达，不使用无限通配的“允许此工具”。
3. 所有调用在执行前检查；授权只在工具成功后消费，失败调用可以合理重试。
4. 未知工具、缺失契约和无法绑定的参数统一进入 `review`。
5. 授权账本可序列化，能够跨进程和长程会话恢复。

跨 benchmark 时，以上规则不应为了实验数字而修改。新环境只增加事件适配、工具效果契约和可泛化的用户表达。

## 4. 与相关工作的关系

### CaMeL

CaMeL 从可信用户请求生成受限程序，将规划模型与读取不可信数据的模型隔离，再通过 capability 和数据流策略阻止外部内容改变控制流。它提供了“授权必须来自可信侧”的重要基础，但严格预生成控制流在动态任务中可能阻断由正常 observation 决定的合理步骤。

我们同样把可信用户侧作为授权根，但不要求预先生成完整程序。当前调用可以动态产生，只要它能与跨轮授权账本对齐；无法对齐但可能合理的调用进入复核，而不是一律视为攻击。

### AUTHGRAPH

AUTHGRAPH 从用户请求生成授权图，并将实际执行的 provenance graph 与之对齐，检查工具和参数来源。它与我们的方向最接近，说明“用户授权与执行来源分开建模”是合理研究路线。

我们的进一步研究对象是长程任务中的**授权状态演化**：用户指令会追加、撤销或延迟授权，文件和记忆也会形成多个版本。即使最终工具和参数来源看似合法，仍需判断被使用的版本此前如何形成、相应修改在当时是否获得授权。

目前不能宣称这部分已经完成。现有程序实现的是授权账本与调用前检查；来源—版本证据和选择性语义审计是下一阶段需要实现并与 AUTHGRAPH 正面对比的部分。

## 5. 可直接使用的程序

核心实现位于：

- `src/greatwallguard/programmatic_guard.py`：公开运行时模块；
- `tests/test_programmatic_guard.py`：接口、隔离、消费和状态恢复测试；
- `experiments/programmatic_effect_guard_v1.py`：旧实验兼容入口；
- `experiments/large_scale_authorization_v1.py`：现有数据回放入口；
- `experiments/large_scale_authorization_v1_results.json`：冻结的逐 case 结果。

最小接入只需要三个调用：

```python
from greatwallguard import ProgrammaticAuthorizationGuard

guard = ProgrammaticAuthorizationGuard()

guard.on_user_message(user_text, turn=turn, trusted=True)

decision = guard.before_tool_call(
    tool_name,
    arguments,
    turn=turn,
    call_id=call_id,
)

# 根据部署策略处理 decision.verdict 后执行工具。
# 工具返回时通知 guard；失败不会消费授权。
guard.after_tool_result(call_id, succeeded=not tool_error)
```

运行模块测试：

```bash
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src:experiments \
python3 -m unittest tests.test_programmatic_guard \
experiments.test_programmatic_effect_guard_v1 -v
```

运行仓库回归测试：

```bash
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src:experiments \
python3 -m unittest discover -s tests -p 'test_*.py'

PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src:experiments \
python3 -m unittest discover -s experiments -p 'test_*.py'
```

更完整的接口与状态恢复说明见 [Programmatic Core v0.1](PROGRAMMATIC_GUARD_MODULE.md)。

## 6. 当前实验结论

模块在 570 条真实 Agent 轨迹、5,674 次工具调用上完成回归。模块化前后逐调用判定完全一致。

| 指标 | 结果 |
|---|---:|
| 具有明确攻击目标调用的攻击 | 258 |
| 高置信 `alert` | 63/258（24.4%） |
| 进入 `review` | 195/258（75.6%） |
| 正常任务明确误报 | 0/265（0%） |
| 正常任务进入 `review` | 79/265（29.8%） |

如果把 `alert` 和 `review` 全部阻断，可检查攻击检出率为 100%，但正常任务假阳性率为 29.8%。这说明当前程序层已经能稳定发现显式越权，真正需要推进的是如何正确处理 `review`，而不是继续堆叠正则规则。

另外 47 条输出或状态完整性攻击没有独立的目标工具调用，不能由调用前检查单独覆盖，需要状态变化和最终输出审计。

## 7. 下一步协作任务

### 任务 A：AgentDojo 适配与固定轨迹评估

目标是在不改核心算法的前提下，将 AgentDojo 的用户消息、工具调用和返回接入三个公开接口。

必须同时报告：正常任务、无防御成功攻击、`allow/alert/review` 分布，以及按工具和攻击类型划分的失败原因。先用固定轨迹验证检测机制，再用少量真实重放验证在线效果；模型自然拒绝攻击不能计作防御成功。

### 任务 B：授权提取评估

为用户消息建立独立金标：允许的效果、对象、具体参数、待外部资料补全的字段、次数和时效条件。比较规则提取与 LLM 提取，但两者必须经过相同的结构校验，不能让 LLM 直接决定放行。

### 任务 C：参数来源与状态版本证据

对 `review` 调用连接已有事实图，回答三个问题：参数来自哪次读取、读取的是哪个对象版本、该版本此前的写入是否获得当时授权。候选字符串匹配不能作为因果证明；无法建立可靠关联时必须保留不确定。

### 任务 D：选择性 LLM 审计

只审计程序层无法确定的局部问题，而不是把完整长上下文再次交给 LLM。输入应至少包含当前授权、待审调用、相关来源和版本证据；输出限定为授权、未授权或证据不足，并保存引用依据。

## 8. 实验纪律与合并要求

- 检测器不得读取攻击标签、成功 oracle 或未来事件；
- 不得在同一测试集上反复修改规则并把结果称为泛化性能；
- 新工具首先登记 effect 和关键参数契约，不能仅凭工具描述授予权限；
- 分开报告 `alert`、`review` 和最终阻断，不把待复核冒充高置信检出；
- 每项改动必须说明解决了哪类失败，并同时检查攻击检出与正常任务误报；
- 新 benchmark 的首轮结果冻结后，再讨论是否升级核心算法版本。

## 9. 当前最重要的研究判断

当前方案并不是“规则检测器加一个通用 LLM”。更准确的结构是：

```text
可信用户侧形成可验证授权
        +
程序侧记录并检查执行事实
        +
只对来源、版本或语义仍不充分的局部调用进行审计
```

后续方法先进性应来自：在动态、多轮、状态持续变化的任务中，用更少的语义审计获得更低误报，同时仍能识别由多个局部合理步骤形成的越权效果。该结论必须通过 AgentDojo、现有长程 case 和后续跨 benchmark 实验共同验证。
