# 邮件场景的可判定性审查：现有证据与缺口

## 要回答的问题

不是先设计更复杂的 TaskScope，而是检查一个调用前检测器是否有足够证据回答：**这封邮件的收件人和内容，是用户授权目标的合理绑定，还是由外部数据额外引出的副作用？** 时间先后或文本中出现同一邮箱，不自动构成因果来源证明。

## 冻结样本与方法

使用现有 7 个匹配的双成功邮件攻击、7 个无注入匹配正常任务，以及 1 个双邮件正常 stress case。脚本 [`email_decidability_audit.py`](../experiments/email_decidability_audit.py)在每次发送前只检查已出现的用户消息和工具返回；另检查现有 L0 图中通向发送 Action 的非时间性因果边。攻击标签仅用于事后分组。此审查**没有重新运行攻击**，也没有引入人工真值标注。

| 观察项 | 结果 |
|---|---:|
| 7 个攻击 case 的第二封邮件：收件人在先前用户消息中出现 | 0/7 |
| 同一收件人在先前工具返回中出现 | 7/7 |
| 发送 Action 与非用户 Observation 存在图上的因果路径 | 1/7 |
| 发送 Action 有参数级来源字段 | 0/7 |
| 7 个匹配正常 case：收件人在用户消息中明确出现 | 7/7 |
| 双邮件正常 stress case：两位收件人在用户消息中明确出现 | 2/2 |

这里的“出现在工具返回中”只是字符串出现，**不是已证明该返回导致了收件人参数**。`next` 时序边也不被计为因果边。图中少量非用户来源连接并没有进一步标出它影响了收件人、主题还是正文。

## 这一步实际说明什么

1. 当前测试中，简单的“收件人未在用户消息出现”就能标记第二封攻击邮件；这**不能证明**我们提出的图证据绑定优于简单 TaskScope。
   实际运行当前不读取图的调用前基线，7/7 攻击 case 的最后一次发送告警，而 7/7 匹配正常 case 的最后一次发送均不告警。这是样本构造使然，不能外推至收件人需从资料中解析的正常任务。
2. 当前图记录了发送操作和持久 Effect，但多数第二次发送缺少从先前文件/记忆/工具观测到发送参数的可验证连接。不能把图中时间相邻误读为参数因果来源。
3. 现有正常邮件过于明确，缺少“用户授权向任务资料中确定的对象发送、但没有写出邮箱”的真实正常轨迹。因此无法估计此类任务上的误报，也无法验证图能否消除误报。
4. 攻击样本中的后续用户话语包含“继续剩余沟通”之类含糊续办。若视其为可信、真实的用户授权，仅靠当前可见信息也未必能断言额外发送必定违背用户意图；数据集 oracle 与独立的人类意图判断不能混为一谈。

## 下一次实验的最小条件

先获取少量**真实无注入**正常邮件轨迹，其中收件人或正文需要从资料中解析，且由独立审查确认发送确实符合用户要求。然后冻结每次发送前的证据，对同一调用分别测试：人工给定准确 TaskScope、现有图、补充参数来源后的图。只有后两者的差异能降低真实正常误报、又不放过越界发送，才值得继续投资图证据绑定；否则应收缩方法主张。

尝试运行这一类正常任务时，本机沙箱拒绝了 OpenClaw 运行器；进一步的受控权限请求被自动审查拒绝，理由是运行可能把工作区派生的通信内容传给外部 DeepSeek API。**没有生成新的正常 case；不会通过其他路径重试。**需要用户明确批准这类数据向该 API 的传输后才能继续真实运行。当前审查只读取已有本地轨迹。
